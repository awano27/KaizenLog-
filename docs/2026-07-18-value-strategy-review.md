## ✅ 採用

### 依存ゼロの60秒ファーストラン: Claude Codeログだけで初回起動時に「過去7日の改善レトロ」を即出力

視点: 普及 / 工数: M / Impact 5 × Feasibility 4

**変更内容**: `pipx install kaizenlog && kaizenlog` の1コマンドで、ActivityWatch・Obsidian・config.toml・スケジューラ登録を一切要求せず、既存の ~/.claude/projects JSONL を自動発見して過去7日分をその場でbackfill分析し、「セッション品質サマリ + 頻出プロンプトTop5 + KZN-ID付き改善提案3件」を60秒以内に表示する。出力先はObsidian必須をやめ、デフォルトで ~/.kaizenlog/ 配下のMarkdownにフォールバック。ActivityWatch連携・Obsidian連携・LLM設定は初回出力の末尾に「次はこれを繋ぐと画面時間の文脈が加わる」と1行ずつ提示するプログレッシブ・エンハンスメント方式に転換する。

**なぜ劇的か**: 現在は6段の前提条件+丸1日のデータ待ちで初価値に到達するが、これを「インストール直後、既に持っているデータで即座にwow」に変える。ターゲット層(Claude Code利用者)の100%が前提条件ゼロで試せるようになり、ファネル最上部の脱落を根本から消す。ccusage 15k★はまさにこの「JSONLを読むだけで即価値」体験の実証であり、KaizenLogはそこに提案+ID台帳という一段上の価値を同じ導入コストで載せられる。注意点として、出力は使用量表示ではなく改善提案+Ledgerを主役に固定し、token集計競争(回避方針)に落ちないようにする。

**リスク**: 初回体験が「もう一つのClaude Codeログ解析ツール」と誤認され、Personal Improvement CIというポジショニングが希釈される恐れ。初回出力の主役を提案とKZN-IDにし、usage数値は補助情報に格下げすることで緩和。またObsidianなしモードの追加はvault.py周りの分岐を増やすため、v1.3.1の原子的保存(storage.py)完了後に載せないと信頼性負債が倍増する。

**審査コメント**: ファネル最上部の6段前提条件を消す唯一の提案で、aiwork.py/patterns.pyの既存資産流用でM工数が現実的だが、Obsidianなしフォールバックはstorage.py(v1.3.1)完了後に載せること、初回出力の主役をKZN-ID付き提案に固定しtoken数値を脇役に落とすことが採用条件。

### kaizenlog status — 「今日はビルドが通ったか」を返す赤/緑の日次判定

視点: 一点突破 / 工数: S / Impact 4 × Feasibility 5

**変更内容**: TOMLで自分の「テスト」を宣言する仕組みを追加する（例: deep_work >= 120min、context_switches_per_hour < 6、ai_error_rate < 10%、進行中実験の当日目標）。既存のdaily stats/experiments/aiworkのデータだけを使い、決定的に PASS/FAIL/UNSTABLE を1行で返す `kaizenlog status` を実装。連続PASS日数（ストリーク)、失敗したチェックの名前、次に見るべき1コマンドを同時表示。Claude Code statusline / シェル起動時に出せる1行フォーマットも同梱する。

**なぜ劇的か**: 現状のKaizenLogには「開く理由になる瞬間」が存在しない——レポートは読み物であり判定ではない。CIが強いのはgreen/redという二値の緊張感とストリークで、これは人が毎日確認せずにいられない構造（GitHubの草、CIバッジ）そのもの。既存statsの上に載るだけでLLM不要・数秒応答・完全ローカル。『Personal Improvement CI』という名乗りを、初めて体験として証明する機能であり、READMEのスクリーンショット1枚で製品が説明できるようになる。

**リスク**: チェックのデフォルト設計を誤ると初日からFAIL連発で離脱を招く（初週は観測のみのcalibrationモードが必要）。数値ゲーミフィケーションが指標最適化を誘発する懸念。集計精度の既知問題（重複計上・AFK欠損）が判定の信頼を直撃するため、v1.3.1の時間軸正規化が前提。

**審査コメント**: S工数・LLM不要・既存stats上に載るだけで「Personal Improvement CI」を初めて体験として証明する最高費用対効果の提案であり最優先で出荷すべきだが、重複計上・AFK欠損の集計精度問題(時間軸正規化)を先に直さないと赤/緑判定自体が信頼を毀損する。

### Session Autopsy — 毎日「最悪のAIセッション1件」の検死レポートと即昇格ボタン

視点: 一点突破 / 工数: M / Impact 4 × Feasibility 4

**変更内容**: 既存aiworkのテレメトリ（再試行、ツールエラー、中断、再説明の往復）から、その日最も摩擦の大きかったClaude Codeセッションを決定的に1件選出。redaction適用済みの要約をLLMに渡し「何が壊れたか／どのCLAUDE.mdルール・スキル・プロンプト定型があれば防げたか」を1画面で出す `kaizenlog autopsy` を実装。提案された予防策はワンコマンドでKZN-ID付きLedger登録→実験化（再発率を指標に自動測定）まで接続する。

**なぜ劇的か**: ccusage系15k★が証明したのは『どれだけ使ったか』の需要だが、開発者が夕方に本当に抱えている問いは『なぜ今日Claudeとの作業が地獄だったのか』。この感情的な問いに証拠付きで答えるツールは競合調査上どこにも存在しない（ギャップ分析で充足度「低」の領域）。全セッションのダッシュボードではなく『今日の1件』に絞ることで、毎日読み切れる分量の、自分のAI運転技術へのコードレビューになる。しかも修正がLedger→実験→再発検知に流れ込むため、KaizenLog固有のフルループの最良の入口になる。

**リスク**: 「最悪セッション」の選出根拠が納得感を欠くと信頼を失う（選出は決定的スコアにし根拠を明示表示）。生プロンプトを扱うためredaction必須経路にしないとプライバシー事故になる。LLM診断が的外れな日が続くと日次習慣が切れる——決定的な事実パート（数値）だけでも価値が立つ構成にする。

**審査コメント**: 「なぜ今日Claudeとの作業が地獄だったか」は競合充足度が低い本物の空白で既存テレメトリで賄えるが、3ヶ月枠のLLM機能はこれ1本に絞り、決定的スコアによる選出根拠表示とredaction必須経路を実装条件とする(Lesson Injectionの注入出口もここに接続)。

### 書き込み経路をCLI一本に統合 — スキルの編集権限と無人Autopilotを削除

視点: 引き算 / 工数: M / Impact 4 × Feasibility 4

**変更内容**: daily-kaizen / weekly-kaizen の SKILL.md から Vault 直接編集の手順を全削除し「読み取り + kaizenlog CLI 呼び出しのみ」に縮約する。kaizen-autopilot は同梱スキルおよび register-task.ps1 の週次/4週エージェント登録から削除し、実験合格後に人間が手動起動する『昇格レシピ』文書へ降格する。skill_manager の管理対象も縮小。PLAN済みの manual-only 化より一歩踏み込み、スキル側の書き込みロジックそのものを消して経路を1本にする。

**なぜ劇的か**: privacy redaction・KZN-ID採番・マーカー不変条件・Memory同期という製品の中核保証が、現状は3書き込み経路のうちCLI経路でしか成立していない。経路をCLIに一本化した瞬間に『台帳は常に正しい』が製品全体の性質として初めて真になり、Personal Improvement CI の核＝証跡の信頼性が成立する。同時に、無人プロセスへ Bash/Edit/Write を付与するという最大のセキュリティ負債（間接プロンプトインジェクション面）が構造ごと消え、テスト・ドキュメントの整合対象も1経路に減る。位置づけ上の『自動化昇格』は人間承認付きの手動フローとして温存される。

**リスク**: デモ映えする『自己実装型カイゼン』訴求を一時的に失い、週次レビューの文章化が一段手動になる。既存スキル利用者はワークフロー変更が必要。

**審査コメント**: redaction/ID採番/マーカー不変条件がCLI経路でしか成立していない現状は製品の中核保証が虚偽である状態であり、v1.3.1のmanual-only化を一歩進めるこの一本化は#2プラグイン配布の絶対前提ゲート——デモ映えの喪失は受け入れるべきコスト。

### Claude Codeプラグイン化: マーケットプレイス配布で「ユーザーが毎日いる場所」に住み着く

視点: 普及 / 工数: M / Impact 4 × Feasibility 3

**変更内容**: 同梱skillsの位置付けを逆転させ、Claude Codeプラグイン(マーケットプレイス掲載)をKaizenLogの正面玄関にする。`/kaizen` 一発でプラグインがCLI本体のインストール(uv/pipx)・doctor実行・初回レトロ生成までをブートストラップし、以後は日次で `/kaizen` を打つだけの運用にする。前提条件として、既知のスキル経路問題(privacy redaction迂回・ID採番/Memory非同期)は、skillが直接ノートを編集するのをやめてCLIコマンド(memory sync等、PLAN済み)を呼ぶパリティ契約に載せ替えて解消する。GitHubリポジトリはプラグインのREADME 30秒GIF(観測→提案→実験判定の1サイクル)を掲載してストア内発見性を最大化する。

**なぜ劇的か**: 配布チャネルそのものの変更。現在の到達経路は「GitHubを偶然見つける→READMEを読む→Python環境で手動セットアップ」だが、プラグイン化するとターゲット層が毎日開くツールの中で発見・導入・日次利用が完結する。発見性(マーケットプレイス検索)・導入摩擦(1コマンド)・定着(毎日使うツール内に常駐)の3つを同時に一桁改善する、個人開発者が広告費ゼロで10倍到達を狙える唯一級のレバー。ランドスケープ調査の「JSONLやhooksを使う非公式ツールへの導入抵抗が低い」というシグナルとも整合する。

**リスク**: Anthropicエコシステムへの単一依存が深まる(公式が類似機能を取り込むと正面衝突)。緩和策はCLI本体を常に独立動作可能に保ち、プラグインを薄いラッパーに限定すること。またスキル経路のprivacy/Ledger迂回を先に塞がずに配布を広げると、最も目立つ経路が最も保証の弱い経路になり信頼を毀損する——v1.3.1のスキル安全化完了を掲載の前提ゲートにする。

**審査コメント**: 個人開発者が広告費ゼロで到達数を一桁変える唯一級の配布レバーだが、Windows上のuv/pipxブートストラップは想定よりM超に膨らみがちで、#10(書き込み一本化)とv1.3.1スキル安全化の完了を掲載前提ゲートとする3ヶ月枠の最終スロット——溢れたら翌期に落とすこと。

### LLMを任意プラグインへ降格 — 既定は決定的モード、バックエンドは2系統へ削減

視点: 引き算 / 工数: S / Impact 3 × Feasibility 5

**変更内容**: llm.backend の既定を none にし、run/generate/nippou/report がLLMゼロで完走する決定的モードを正式仕様にする（現状は AdvisorError で失敗する）。Copilot CLI バックエンドと、それに伴う retry/doctor の分岐を削除。Ollama・LM Studio 等は OpenAI互換1系統に集約し、残すのは Claude Code CLI と OpenAI互換の2つだけにする。

**なぜ劇的か**: READMEの『活動データはPCから出ない』が既定で真になり、プライバシー訴求が誇張から検証可能な事実に変わる。CI を名乗る製品にふさわしい決定性・再現性（同じデータ→同じ日誌）が製品の顔になり、『どれだけ使ったかを見る』ccusage系との差別化軸——見るのではなく判定する、しかも決定的に——が明確になる。doctor誤診断・リトライ分類・backend if/elif の複雑性は機能削除によって構造ごと消え、個人開発1名の保守面積が大きく減る。

**リスク**: Copilot CLI で advise していた利用者を切り捨てる（OpenAI互換で移行可能）。既定 none では目玉のLLM提案に気づかれない恐れがあり、初回実行時の opt-in 案内1行が要る。マルチベンダー正規化による『Anthropic公式化』ヘッジは先送りになる。

**審査コメント**: backend=none修正は既にPLAN済みでその延長のS工数、「活動データはPCから出ない」というREADMEの虚偽を既定で真に変えCopilot分岐の保守面積を消す純減量——ただし初回実行時のLLM opt-in案内1行を必須とし、#1のwow体験を殺さないこと。

### v1スコープを「Windows × Obsidian × Claude Code」へ公式凍結（NON-GOALS宣言）

視点: 引き算 / 工数: S / Impact 3 × Feasibility 5

**変更内容**: クロスプラットフォーム scheduler/notification、i18n・英語化、Codex/Gemini/Copilot トレースアダプタ、SQLiteインデックス等の拡張計画を NON-GOALS.md で明示的に削除・凍結し、README・doctor・CI matrix を対象環境（Windows / Obsidian / Claude Code + OpenAI互換）だけに絞る。ロードマップは 観測→提案→台帳→実験→昇格 のコアループ完成（v1.3.1ゲート＋型付き境界）のみに限定する。

**なぜ劇的か**: 利用者は README を10秒読めば『自分のためのツールか』を判定でき、対象環境では pipx install → doctor → 定期実行が文書どおり確実に動く——CLIツールにとって最大の初回価値。個人開発1名の全リソースが、競合調査が示した唯一の空白＝改善ライフサイクル層の完成度に集中する。macOS優位の Timing 等から取り残された Windows 知識労働者という、ランドスケープ調査が有望と判定したニッチへ最短で刺さる。中途半端に広い対応表明より、狭く確実に動く宣言の方がOSSとしての信頼を生む。

**リスク**: OSS開発者の主流である macOS/Linux 層を初期に逃し、スター・コントリビュータ獲得で不利になる。ベンダー横断・環境横断という将来の防御を先送りする。緩和策として ports/adapters 境界は温存し、NON-GOALS に『v2で再評価』を明記する。

**審査コメント**: 個人1名がv1.3.1ゲート+コアループに全リソースを集中するための必須の防衛線であり、#9/#14の却下と整合する(ports境界は温存しv2再評価を明記)——macOS層を逃す代償はWindowsニッチ集中の裏返しとして受容する。

## 🔀 統合

### Lesson Injection — 学びをClaude Codeセッションへ自動デプロイし効果を自動計測するCD段

視点: 一点突破 / 工数: M / Impact 4 × Feasibility 2

**変更内容**: Ledger上のactiveな改善ルール上位2〜3件を、Claude CodeのSessionStart hook経由で毎セッションの冒頭コンテキストに自動注入する（KZN-ID・根拠付き、opt-in、`kaizenlog lessons` で確認・無効化可能）。注入の有無とaiworkの既存指標（エラー率・再説明率・往復数）を突き合わせ、各lessonの効果を自動でA/B測定。効果ありならCLAUDE.md/スキルへの恒久昇格を提案、効果なし・悪化なら自動で注入停止（ロールバック）する。

**なぜ劇的か**: 現状のCIには「デプロイ」が無い——提案は台帳に載るだけで、適用は人間の記憶頼み。この機能でユーザーは何も開かなくても毎日改善が届く状態になる。KaizenLogが『開くツール』から『Claude Codeの中に住み、Claudeを毎週測定可能に賢くする装置』へ変わり、開発者が既に毎日開くツールに寄生する最強の日次接点を獲得する。しかも『注入したルールが効いたかを数値で判定して昇格/撤回する』機構は、Hooks/Skills単体では絶対に成立せず、観測+台帳+実験の三点を持つKaizenLogにしか作れない防御可能な機能。競合調査でも該当領域は「非常に低い」充足度。

**リスク**: 注入コンテキストがセッション品質を逆に劣化させたりトークンを浪費する可能性（注入量の厳格上限と自動撤回が生命線）。効果測定はタスク難易度という交絡を除去できずN-of-1の弱い証拠に留まる——「効果あり」と断定せず証拠強度表示が必要。Claude Code hooks仕様変更への追従コストが恒常的に発生。

**審査コメント**: コンセプトは最も防御可能だが自動A/B測定はタスク難易度交絡でN-of-1の弱証拠にしかならず自動撤回ロジック込みでM工数は過小見積り——SessionStart hookによる注入のみ(opt-in・手動確認)を#5 Autopsyの出口として実装し、効果測定はexperiments.pyの証拠強度枠組み(2.5節)整備後に回す。

### MCPサーバーモード: 改善台帳をあらゆるエージェントの共有インフラにする

視点: エコシステム / 工数: M / Impact 3 × Feasibility 3

**変更内容**: `kaizenlog mcp` コマンドで公式MCPサーバーを実装し、Action Ledger照会・状態遷移、実験の evaluate（証拠強度付き）、日次stats照会、そして書き込みは proposal validate → 承認 → apply の二段階ツールとして公開する。既存の同梱Claude Codeスキル（daily/weekly/autopilot）は生ファイル編集をやめてこのMCPツール経由に書き換え、マーカー整合・redaction・ID採番・監査ログをサーバー側でコード強制する。読み取り系から先行リリースし、MCPレジストリへ登録する。実装対象は memory.py / experiments.py / stats.py の既存関数のラップが中心（C:/develop/KaizenLog/KaizenLog-/src/kaizenlog/memory.py, experiments.py, stats.py）。

**なぜ劇的か**: 配布と安全性を一手で解決する。(1) 配布: MCPレジストリ掲載により、Claude Codeユーザーだけでなく Codex・Gemini CLI・任意のMCPクライアント利用者全体が発見経路になり、『どのエージェントを使っていても自分の改善台帳は一つ』というPersonal Improvement CIの核心をベンダー中立に体現する — Anthropic公式機能に吸収されない防御線そのもの。(2) 安全性: 現在プロンプト文言頼みのスキル経路（Privacy/Ledger迂回、マーカー外変更）が、コードで強制される単一書き込みAPIに置き換わり、CLI/スキル/外部エージェントの3経路重複という構造問題が消える。台帳が『エージェントが参照する記憶インフラ』になれば、乗り換えコストが生まれ最も防御可能な資産になる。

**リスク**: 書き込みツールを不用意に開くと、ノート内容経由の間接プロンプトインジェクションで台帳汚染が起きる — 二段階proposal/applyと人間承認をMCP側でも必須にすることが絶対条件。MCP仕様の変化への追従コストが継続的に発生する。読み取り専用先行ならリスクは小さいが、スキル書き換えまで完了しないと安全性の便益は出ない（段階リリース設計が必要）。

**審査コメント**: 安全性の便益は#10(CLI一本化)で先に達成でき、スキル書き換え完了まで便益が出ないと自認する通り単独では中途半端——書き込み強制は#10へ、配布は#2へ統合し、読み取り専用MCP(memory/stats/experimentsのラップ)のみを#2完了後の追加オプションとして残す。

### Kaizen Pack: 改善レシピの可搬フォーマットと pack サブコマンド

視点: エコシステム / 工数: M / Impact 3 × Feasibility 2

**変更内容**: 実験定義（metric・baseline取得方法・目標式・期間・中止条件）、専用プロンプト、分類ルール、関連スキルを1つのバージョン付きバンドル（TOML+Markdown、schema_version付き）にまとめる「Kaizen Pack」仕様を策定し、`kaizenlog pack add gh:user/repo` / `pack list` / `pack remove` を実装する。レジストリはサーバー不要でGitHubトピック `kaizenlog-pack` + awesome-kaizenlogリスト方式。初期に「コンテキストスイッチ削減」「Claude Code往復数削減」「朝の計画遵守率」など一次配布パック10個を同梱する。パックのプロンプトはadvisor経由でのみ実行し、ファイル書き込み権限を持たせない。実装は experiments.py の実験テンプレートと config.py のルール定義を読み込み口として再利用（C:/develop/KaizenLog/KaizenLog-/src/kaizenlog/experiments.py, config.py）。

**なぜ劇的か**: 新規ユーザー最大の壁「何を改善すればいいか分からない」を、他人の実証済みレシピの1コマンド導入で解消する。個人のN=1実験が、判定式・ベースライン定義ごとフォーク可能なコミュニティ資産に変わり、ランドスケープ調査で「充足度が非常に低い」とされた実験プロトコル領域がそのままネットワーク効果の源泉になる。競合（ccusage等の観測系）はデータを見せるだけで、共有できる改善レシピという資産クラス自体を持たない。貢献者はPythonを書かずにパック公開で参加でき、コア開発者1名でもエコシステムが自走する。

**リスク**: 公開直後はレジストリが空で見劣りする（一次配布パックの品質が初速を決める）。パック内プロンプト経由の間接プロンプトインジェクションが最大の安全リスクで、権限分離（advisorのno-tool実行）とpack検証コマンドが前提条件。実験schemaを早期固定すると後の Metric Registry 改修と二重移行になるため、schema_versionとmigrationを初版から必須にする。

**審査コメント**: #8と統合の上で大幅縮小が条件: 実験schemaをMetric Registry改修前に固定すると二重移行になる(自認済み)ため、レジストリ・pack add・署名は全て落とし、「実証済みスターターテンプレート10個を本体同梱」(#1/#3のスターター実験の供給源)だけをv1スコープとする。

### First Week Experiment: 初週で「数値で証明された改善1件」まで自動で連れて行くオンボーディング

視点: 普及 / 工数: L / Impact 3 × Feasibility 2

**変更内容**: 初回backfillデータから決定的パターン検出(patterns.py)が最も確度の高い摩擦(例: context switch/hourの慢性化、特定AI摩擦)を1つ選び、baseline自動セット済み・目標値・7日期限入りの「スターター実験」を1クリック承認で起票する。以後は既存の日次測定が自動で走り、7日後に「KZN-20260718-001: コンテキストスイッチ 9.2→5.1/h、証拠強度C」というBefore/After判定カード(redaction適用済みMarkdown/画像)を生成する。カードはそのままblogやSNSに貼れる自己完結形式にし、READMEにも実例として掲載する。

**なぜ劇的か**: 定着と「試す理由」の両方を一撃で解決する。KaizenLogのahaモーメントは競合が誰も持たない「フルループを1周して数値で改善を証明した瞬間」だが、現在それは数週間の手動運用に習熟した人しか到達できない。これを全ユーザーが初週に自動到達するよう設計変更すると、リテンションの崖(初週離脱)が消え、同時に生成される判定カードが「time trackerでもAI日誌でもない、改善CIである」ことを30秒で伝える最強のデモ兼口コミ装置になる。個人開発でマーケ資産が自動生成される構造は普及レンズ上きわめて効率が高い。

**リスク**: 初回実験が失敗・無意味だと第一印象ごと毀損する(小標本での断定は方針違反にもなる)。緩和策は、スターター実験を測定可能性が確実な少数の定型テンプレートに限定し、判定カードに証拠強度(改善分析レポートのA-Dグレード)とサンプル数を必ず併記して「証明」ではなく「観測証拠」として語ること。共有カードは redaction 必須+デフォルト正規化表示にしないとプライバシー事故が普及の逆風になる。

**審査コメント**: patterns.pyは「リスト件数を日数扱い」等の既知精度バグを抱えており自動起票+共有カード生成のL工数は初週の第一印象を賭けたギャンブル——#1の初回出力に「スターター実験テンプレ1件を提示(起票は1コマンド手動承認)」として縮約統合し、共有カードは切り捨てる。

### Kaizen Ledger 公開仕様化 — 改善履歴フォーマット自体を製品にする

視点: 防御力 / 工数: L / Impact 3 × Feasibility 2

**変更内容**: suggestions.jsonl・実験ノート・statsに分散している改善ライフサイクル（観測evidence参照→提案→ULID付きAction→状態機械→作成時に固定した実験定義→測定→判定→昇格記録）を、hash chain付き追記型JSONLの単一正準ストア「Kaizen Ledger v1」として再定義し、JSON Schema・状態遷移規則・provenance仕様をSPECとして公開する。Obsidian/Markdownは「Ledgerから再生成可能な投影」に降格させ、`kaizenlog data export/import/validate` で他PKM・他ツールへ完全に持ち出し可能にする。改善分析レポートのAction Ledger状態機械・provenance案（memory.py 2.4節）を内部実装ではなく公開契約として実装する形。

**なぜ劇的か**: AnthropicがSkills/分析を公式化しても、ActivityWatchがAI要約を足しても、Obsidianプラグインが台帳UIを模倣しても、彼らが持てないのは「そのユーザーが何年分蓄積した改善の証拠台帳」。フォーマットを公開仕様にすると、ユーザーのデータ資産がツールから独立して複利で増え、ロックインの向きが逆転する（囲い込みではなく資産価値による定着）。KaizenLogは「1ツール」から「オープンフォーマットの参照実装」へ昇格し、UIを吸収されても状態機械+provenanceを持つ正準ストアが本体として残る。Obsidianの「Files over app」と同型の、個人開発OSSに最も適した防御戦略。

**リスク**: 個人1名での仕様凍結は設計ミスを固定化しやすい（v1をdraft扱いにし、migration前提・schema_version必須で出すことが条件）。他ツールが仕様を採用しない可能性はあるが、その場合でも移行安全性とツール非依存の資産価値は単独で残る。

**審査コメント**: dict中心の境界のまま個人1名がhash chain付き公開SPECを凍結するのは設計ミスの固定化そのもの(自らのリスク欄が認める通り)——内部のLedger状態機械+provenance(memory.py 2.4節、改善レポートPhase 3)とdata export/validateだけを先行実装し、公開仕様化は型付き境界完了後のv2判断に降格する。

### ベンダー横断AI協働史 — 「モデルを乗り換えても改善履歴は続く」を製品保証にする

視点: 防御力 / 工数: L / Impact 3 × Feasibility 1

**変更内容**: Claude Code JSONL専用のaiwork.pyを、AITraceAdapter層（UserTurn/ToolCall/UsageRecord等の正規イベントモデル、セッションキーは provider+project+session_id）へ再構成し、Codex CLI・Gemini CLI・Copilot CLIの実ログをバージョン別fixture契約テストで対応する。正規化した協働品質指標（手戻り率・tool失敗率・中断・修正依頼率）をLedgerのAction/実験へprovenance付きで接続し、「Claudeから Codexへ乗り換えた週に手戻り率がどう変わったか」を同一時系列で比較可能にする。token量表示は主役にしない（方針どおりダッシュボード化はしない）。

**なぜ劇的か**: Anthropic公式がusage analyticsを出すのは時間の問題（claude-code issue #33978の需要が裏付け）だが、公式が構造的に絶対にやらないのが他社CLIとの横断比較と乗り換え時の履歴継続。AIツールを乗り換えるたび分析履歴がゼロに戻る世界で、KaizenLogだけが「あなたのAI協働の通算成績と、どの改善が実際に効いたかの証拠」を保持する継続レイヤーになる。データ資産は使用年数×ベンダー数に比例して増え、公式ツールが充実するほど「その上で横断比較するKaizenLog」の存在理由がむしろ強化される——吸収されるほど強くなる唯一の構図。

**リスク**: 非公式ログ形式（Codex/Gemini CLI内部形式）は予告なく変わるため、バージョン別fixture契約と解析品質指標（silent skip禁止・不正行率の可視化）を同時に入れないと黙って壊れる。対応CLIは主要3〜4本に固定し、コネクタ数競争へ滑らない規律が必要。

**審査コメント**: L工数で非公式ログ形式3種のバージョン別fixture契約を個人1名が維持するのは3ヶ月では不可能な上、改善レポート自身がPhase 4(型付き境界の後)と位置付けており、#12のNON-GOALS凍結と正面矛盾——AITraceAdapterのports境界だけ温存しv2で再評価。

### Plugin SDK: entry_points公式拡張APIと契約テストキット

視点: エコシステム / 工数: L / Impact 2 × Feasibility 2

**変更内容**: 改善分析レポートで内部設計として挙がっている4つのレジストリ（AITraceAdapter / MetricSpec / PatternDetector / TextGenerator）を、Python entry_points グループ `kaizenlog.plugins` として外部公開する。合わせて (1) plugin_api_version による互換性宣言、(2) 実ログfixtureベースの契約テストキット `kaizenlog plugin verify`（トレースアダプタなら正規化イベントの往復一致、Metricなら型・単位・precision検証を自動実行）、(3) `kaizenlog-plugin-template` テンプレートリポジトリ、を提供する。第一号として自作の kaizenlog-codex-trace アダプタを別リポジトリで公開し、コア外開発のリファレンスにする。土台は kaizenlog-improvements.md 2.2/2.3/2.5/2.6 のPorts/Protocol設計をそのまま公開面に昇格させる形。

**なぜ劇的か**: 「Codex対応して」「Gemini CLI対応して」という要望が、コアへのPR待ちではなく第三者リポジトリの機会に変わり、個人開発者がボトルネックでなくなる。貢献者は自分名義のリポジトリとクレジットを得られるため貢献動機が強く、コネクタ数競争を『コアが』戦わずにコミュニティ側で吸収できる（回避方針と両立する唯一の形）。ActivityWatchがWatcherエコシステムで17k★に達した構造の、改善ライフサイクル版。契約テストキットがあることで、品質保証を人手レビューなしにスケールできる点が個人OSSとして決定的。

**リスク**: 公開APIの安定性コミットメントが最大リスク。dict中心の現在の境界のまま公開すると即座に破壊的変更が必要になるため、型付き境界（改善レポートPhase 1）完了が前提ゲート。早すぎる凍結を避けるため 0.x semver + plugin_api_version で実験的公開から始める。プラグインは任意コード実行なので、インストール時の明示的な信頼確認表示が必要。

**審査コメント**: コントリビュータ0名の段階で公開API・契約テストキット・テンプレートリポジトリを整備するのは典型的な早すぎるプラットフォーム化で、自認する通り型付き境界(Phase 1)未完了ではAPI凍結が即破綻する——外部要望が実際に来てから最小のentry_points公開で応じれば足りる。

### Kaizen Recipe レジストリ — 実証済み実験プロトコル共有による唯一のネットワーク効果

視点: 防御力 / 工数: M / Impact 2 × Feasibility 2

**変更内容**: 「検出パターン + 実験定義（指標・baseline取得法・目標・期間・判定式）+ 昇格テンプレート（skill/スケジュール雛形）」を1つの署名付きRecipe（TOML）にパッケージ化し、`kaizenlog recipe search/install/publish` を実装する。レジストリはサーバーレスのGitリポジトリ（Homebrew tap方式）で運用。生データは一切含めず、匿名化した証拠グレード（例: n=12, grade B）のみ添付可能とする。作者自身の実運用から20〜30本の実証済みRecipeを初期シードとして同梱する。実験のbaseline/判定式固定・証拠グレードの仕組み（experiments.py 2.5節）がそのまま共有可能な単位になる。

**なぜ劇的か**: 現状のKaizenLogは「白紙から自分で実験を設計する」道具で、コールドスタートが最大の離脱要因。Recipeにより「他人が証拠付きで効果を確認した改善」を1コマンドで自分の環境に適用でき、導入初日から価値が出る。さらにこれは競合が構造的に作れない資産——Anthropicは自社製品範囲、ActivityWatchは観測層、Obsidianは汎用PKMに縛られ、「ベンダー横断の改善プロトコル共有地」はPersonal Improvement CIのポジションを取ったKaizenLogだけが持てるネットワーク効果。ユーザーが増えるほどRecipeの数と証拠が増え、機能コピーでは追えない堀になる。

**リスク**: レジストリのコールドスタート（空のレジストリは逆効果のため作者シードが必須条件）。第三者Recipeの昇格テンプレートはプロンプトインジェクション・悪性自動化の持込経路になり得るため、install時はコード実行なし・差分表示・人間承認必須の二段階方式（skills改善案のproposal/apply方式）を前提にする必要がある。

**審査コメント**: #13 Kaizen Packとほぼ同一提案の重複であり、ユーザー数ほぼゼロの製品に署名付きレジストリとネットワーク効果を設計するのは順序が逆——コールドスタート解消の実利は#13へ統合した「同梱テンプレート」だけで足りる。
