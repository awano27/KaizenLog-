## 本弾の性格(実装前に必ず理解すること)

これは初のリアルタイム機能。審査で指摘された2大リスクは **(a) フック起動レイテンシ(Windows で Python 冷起動は数百ms)** と **(b) 書き込み途中 JSONL の tail 堅牢性**。本指示書はこの2つを仕様として契約化する:

- フックは **UserPromptSubmit と Stop のみ**。**PostToolUse には登録しない**(ツール呼び出し毎の起動はレイテンシ税が非受容。リトライ連鎖はユーザー発話ベースなので UserPromptSubmit で検知可能、ツールエラー連続は Stop で足りる)
- 状態キャッシュによる**増分 tail**(毎回の全量再パース禁止)と**デバウンス早期終了**を必須とする

## Phase 1 — §A: guard コア

### §A1 検知エンジン(新規 `src/kaizenlog/guard.py`)

- **エントリ**: `python -m kaizenlog.cli --config ... guard --hook` を Claude Code フックのコマンドとして使う。stdin から フック JSON を読む(`session_id`・`transcript_path`・`cwd`・`hook_event_name`・UserPromptSubmit なら `prompt`)。**キー欠落・JSON不正は exit 0**(寛容パース)
- **状態キャッシュ**: `%LOCALAPPDATA%/kaizenlog/guard/<session_id>.json` に {transcript オフセット・直近プロンプト列(正規化済み・最大10件)・連鎖長・最終発火時刻・最終解析時刻} を保持。破損時は初期化して続行
- **デバウンス早期終了**: 前回解析から `debounce_seconds`(既定30)未満なら**重い import の前に** exit 0(この判定は stdlib のみで行う。§C1 でテスト固定)
- **増分 tail**: transcript をキャッシュ済みオフセットから読み、**新規行のみ**パース。書き込み途中の最終行(JSON 不完全)は捨てて次回に回す(オフセットは完全行末まで)。ファイル縮小・置換(オフセット>サイズ)は先頭から再読
- **検知(決定論)**:
  1. リトライ連鎖: 新プロンプトを `normalize_prompt_text`(aiwork.py:233)で正規化し、状態内の直近プロンプトと `similarity_ratio`(promptledger.py:122)で照合(閾値は既存 `_RETRY_SIMILARITY`=0.85・窓 `_RETRY_WINDOW_MINUTES`=30 と同値をguard側定数として使用)。類似が続いた回数 >= `retry_threshold`(既定3)で発火
  2. ツールエラー連続(Stop 時): 新規レコード中の連続ツールエラー >= `tool_error_streak`(既定3)で発火
- **浪費推定(取れる場合のみ)**: 連鎖中の assistant レコードの output tokens を合算し `resolve_output_price`(aiwork.py:80)で換算。モデル不明・トークン欠落なら金額を出さない(fail-closed)
- **重い import の禁止**: guard.py のモジュールトップで `cli`/`aiwork`/`promptledger` 等を import しない(関数内 lazy import)。§C1 でテスト固定

### §A2 発火アクション

発火時(クールダウン `cooldown_seconds`(既定300)内の再発火はしない):
1. stdout に フック JSON を出力: `{"hookSpecificOutput": {"hookEventName": "<入力のecho>", "additionalContext": "⚠️ KaizenLog空転ブレーカー: 同趣旨の依頼が3回目です(推定$X浪費中)。アプローチを変える・前提を明示する・手動介入を検討してください。"}}`(金額不明時は金額句を省く。抜粋を含める場合は redact 済みのみ)
2. Windows トースト: `notify.notify`(notify.py:13、lazy import)。失敗しても無視(exit 0 維持)
3. `<memory_path>/live_episodes.jsonl` に append: {ts, session_id, kind: "retry"|"tool_error", chain_len, est_tokens|null, est_usd|null, excerpt(redact済み)}。memory_path 未解決(config無し等)なら記録スキップで続行

### §A3 設定とインストール

- config に `[guard]` 追加(config.py の HandoffConfig(~L150)と同様の dataclass): `enabled=true`・`retry_threshold=3`・`tool_error_streak=3`・`cooldown_seconds=300`・`debounce_seconds=30`。`enabled=false` なら guard --hook は即 exit 0
- CLI(cli.py の subparsers(L2070)配下に `guard` 追加):
  - `kaizenlog guard --hook`: 上記フック動作
  - `kaizenlog guard install`: `.claude/settings.json` に登録すべき hooks スニペット(UserPromptSubmit + Stop、コマンドは絶対パスの venv python + `--config` 焼き込み)を**標準出力に表示するのみ**
  - `kaizenlog guard install --write [--project|--user]`: 対象 settings.json に冪等マージ(既存 kaizenlog guard エントリは置換・他のフックは不可侵)。**書き込み前に `settings.json.bak-<timestamp>` バックアップ必須**。JSON 不正なら書かずにエラー
  - `kaizenlog guard status`: 状態キャッシュ一覧(セッション数・最終発火)と設定値表示

## Phase 3 — §C1: 性能・安全契約のテスト固定

`tests/test_round31_guard.py` に以下を**構造的に**固定する(壁時計時間だけに頼らない):

1. **import 軽量性**: `import kaizenlog.guard` 後に `sys.modules` に `kaizenlog.cli`/`kaizenlog.aiwork`/`kaizenlog.promptledger` が**存在しない**こと
2. **デバウンス早期終了**: 状態キャッシュの最終解析時刻が30秒以内のとき、transcript を**1バイトも読まずに** exit 0(open をモックして呼ばれないことを検証)
3. **増分読み**: 2回目の呼び出しで読むバイト数が新規追記分のみ(read サイズを計測)
4. **不完全行**: 最終行が途中で切れた JSONL で例外なし・次回に完全行として読めること
5. **全例外沈黙**: stdin 不正 JSON・transcript 不在・状態ファイル破損・notify 例外、全ケースで exit 0
6. 検知境界: 類似2回目は非発火・3回目で発火・クールダウン内再発火なし・ツールエラー2連続非発火/3連続発火
7. additionalContext の JSON 形状・redact 適用・金額 fail-closed(モデル不明で金額句なし)
8. install --write: バックアップ生成・他フック不可侵・冪等(2回実行で同一)・JSON不正時ゼロ書き込み
9. 性能スモーク: 合成 transcript(1000行)で guard --hook 1回の処理が2秒以内(緩い上限。CI 揺らぎ考慮)
10. §B1: 日誌の⚡行(0回で非表示)・7日超過状態ファイル削除・doctor 項目
