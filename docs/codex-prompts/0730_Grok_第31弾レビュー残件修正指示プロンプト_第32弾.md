## §R1 debounce_seconds < 30 が本番経路で無効

### 確認済み問題
guard.py:380-388 — 一段目デバウンス判定(config読込前・stdlibのみ)が `_DEFAULT_DEBOUNCE=30` 固定。`debounce_seconds=0` や `5` を設定しても最初の30秒ゲートで弾かれ、実質下限30秒に張り付く(実測: debounce=0 で3連続呼び出しが chain_len=1)。

### 修正契約
- 状態ファイルに **前回実行時に解決した実効 debounce 値**(`effective_debounce`)を保存し、一段目ゲートはこの保存値を使う(stdlib のみで読める)。保存値が無い初回は既定30
- config で値が変わった場合、次の完全実行(二段目通過)時に保存値を更新 → 2回目以降は新値が効く。この「1回遅れで反映」の設計をdocstringに明記
- 一段目が「configより先に走る軽量ゲート」である構造自体は維持する(レイテンシ契約)

### 必須回帰テスト
`debounce_seconds=0` の状態ファイル(effective_debounce=0)で連続3回呼び出し → 3回とも解析が走り chain_len=3。`=60` 保存済みで31秒後呼び出し → 早期終了。

## §R2 install --write が既存の空 hooks ブロックを削除

### 確認済み問題
guard.py:692-705 — 自ブロック判定に `all(...)` を使っており、既存の `"hooks": []`(空リスト)ブロックで `all([])` が True → **他人のブロックがまるごと消える**(実測: matcher="keepme" の空ブロック消失)。

### 修正契約
自ブロック判定を「`hooks` が**非空**かつ全コマンドが kaizenlog guard のもの」に修正(`block.get("hooks") and all(...)`)。空 hooks ブロックは他人のものとして不可侵。

### 必須回帰テスト
空 hooks ブロック(matcher付き)入り settings.json に --write 2回 → 空ブロックがバイト単位で残存+冪等。

## §R3 ⚡日誌カウントのUTC/ローカルTZ不整合

### 確認済み問題
guard.py:274-293(count_live_breaker_fires)+613-615 — live_episodes の ts は UTC ISO 保存だが、cmd_generate から渡る `day` は config TZ(JST等)のローカル日付で、`ts.startswith(day_s)` の文字列前方一致比較。**JST 0〜9時台の発火が当日の日誌に計上されない**。

### 修正契約
- `count_live_breaker_fires(memory_dir, day, *, tz: ZoneInfo)` に変更: 各 ts を `datetime.fromisoformat` でパース→ tz 変換→ `.date() == day` で比較。パース不能行はスキップ(fail-closed)
- 呼び出し側(cmd_generate)は `ZoneInfo(cfg.timezone)` を渡す

### 必須回帰テスト
UTC 2026-07-29T22:30(=JST 07-30 07:30)のエピソード → JST の day=07-30 でカウント1・day=07-29 でカウント0。naive ts・不正 ts 行はスキップ。

## §R4 ツールエラー streak が成功で一切リセットされない

### 確認済み問題
guard.py:490-501 — リセット条件 `rec.get("type") == "tool_result"` は Claude Code JSONL では成立しない(ツール結果は `type="user"` レコード内の `message.content[].type=="tool_result"`)。**成功ツール結果を挟んでも streak が累積し、非連続エラーで誤発火する**。

### 修正契約
- レコード内に「成功した tool_result ブロック」を検出するヘルパー(`_has_successful_tool_result(rec)`: message.content 配列に type=="tool_result" かつ is_error が truthy でない要素がある)を追加し、それで `tool_streak = 0` にリセット
- 同一レコードにエラーと成功が混在する場合の規約: **エラー優先でカウント→その後に成功があればリセットしない**(=エラーを含むレコードはリセットしない)。この規約をコメントに明記
- ユーザー/アシスタントの通常発話ではリセットしない(現仕様維持)

### 必須回帰テスト
エラー2→成功1→エラー2 の列で非発火(リセット確認)・エラー3連続で発火・エラー2+同一レコード内(エラー+成功混在)+エラー1 は発火(エラー優先規約)。

## §R5 doctor の書き込みプローブ副作用

### 確認済み問題
doctor.py:418-423 — 読み取り専用のはずの doctor が `%LOCALAPPDATA%/kaizenlog/guard/` に mkdir+書込プローブを行う。

### 修正契約

### 必須回帰テスト
ディレクトリ不在で doctor 実行 → ディレクトリが作成されない・出力に「未作成」。
