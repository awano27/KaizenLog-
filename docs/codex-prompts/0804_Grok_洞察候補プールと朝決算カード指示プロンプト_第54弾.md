## 設計原則（遵守・違反はレビューで差し戻し）

1. **数字はコード・解釈はLLM** — LLM が数値を生成・改変できる経路を1つも作らない。LLM の権限は「ID を選ぶ」「数字禁止の短文を書く」まで。
2. **契約違反は縮退** — LLM 出力が契約に違反したら決定論出力へフォールバックし、日誌が壊れない（既存の `AdviceContractError` 経路 `cli.py:1837` と同思想）。
3. 評価語・点数化・因果の断定をしない。「観測されています」「因果は断定しません」調。
4. マーカー区間外は1バイトも変更しない。手書き（チェック・理由記入）はシステムが上書きしない。
5. 台帳は追記のみ。既存レコードのフィールド削除・書き換えは行わない（本弾で許可されるスキーマ追加は §T2 の `decision` のみ）。
6. 該当データが無い日は区間・小節ごと出さない。
7. 冪等・fail-closed・既定 config で発火（第51〜53弾と同じ）。
8. 実 LLM 呼び出し禁止（テスト・検証はフェイクのみ）。

## §T1 洞察候補プール — 「🧠 事実からの洞察」（ADVICE 区間内の新設節）

**目的**: digest は評価語禁止の決定論、LLM は数字を書くと契約違反 — 「この数字がこうだった」を一文で言える場所が構造的にゼロ。数字入り候補文をコードが作り、LLM は**選ぶだけ**にすることで、分業原則を崩さず数字と解釈を同居させる。

### T1-1 候補文の決定論生成

新関数 `build_insight_candidates(stats, history) -> list[dict]`（置き場所は advice_evidence.py 内で可）。各候補は `{"id": "C1", "text": "<数字入りの事実文>"}`。最大8本・重要度順。

- 文体は「〜が観測されています」「〜でした」の事実調のみ。評価語（良い/悪い/多すぎ等）・助言・因果断定は禁止。
- 材料（すべて既存 stats/history から。日誌に既出の指標を優先）: retry_chains 件数と7日中央値差 / ended_in_error セッション数と終了時刻帯 / tests_run 関与セッションと非関与の対比 / switch レート（`_switch_rate`）と履歴比 / focus_blocks・focus_minutes（input 欠測日は候補にしない）/ by_site 上位の初出・急増 / loop_tax（episode_count・est_cost_usd）/ outcome_git のコミット集中時間帯。
- データが薄い日は本数が減ってよい。0本なら §T1 全体をその日は出さない。
- 候補文は生成時点で完成文（後から数値を埋める穴なし）。redact 済みフィールド以外の生テキストを使わない。

### T1-2 契約拡張 `insight_selection`

advise の JSON 契約にオプションフィールド `insight_selection` を追加: `[{"candidate_id": "C3", "connector": "一方で"}, …]` 最大2件。

- 検証（`_validate_advice_raise` に追加）: candidate_id はプロンプトで渡した候補 ID 集合の部分集合（`parse_facts` :440-443 と同型のエラー文言）/ connector は省略可・`_require_single_line` + `_DIGIT_RE` 禁止 + `_check_no_kzn_or_marker` + 最大20字。
- プロンプト（`build_prompt`）に候補一覧（ID + 全文）と選定指示を注入: 「今日の文脈で最も重要な洞察を最大2本、ID で選べ。本文の生成・改変は禁止」。
- 候補0本の日は契約フィールド自体を要求しない（渡さない・検証しない）。

### T1-3 レンダリングと縮退

`render_advice_markdown` に節を追加:

```markdown
## 🧠 事実からの洞察
- リトライ連鎖2件はどちらも21時台に発生し、うち1件は末尾エラーのまま終了しています。[C3]
- 一方、テスト実行を伴うセッション3件は連鎖に関与していません。[C5]
```

- 選ばれた候補文は**原文のまま**描画（末尾に [C番号]）。connector があれば2本目の文頭に付す。
- **縮退**: `insight_selection` が契約違反（または欠落）のとき、advise 全体を落とさず**候補上位2本をそのまま描画**する（数字は元々コード生成なので縮退しても品質が落ちない）。既存の修復ループ（`_contract_repair_prompt`）の対象にも含める。
- `_assert_render_shape`（:648）に節の存在検証を追加。

### T1-4 eval 回帰

`eval/samples/` に第54弾ケースを追加し、`tests/test_eval_samples.py` の流儀で: (a) 候補 ID 以外（例 "C99"、自由文、数字入り connector）を返すフェイク応答が契約違反として検出される、(b) 縮退で候補上位2本が出る、の回帰を固定する。

**受け入れ条件**: LLM 応答のどのフィールドからも数値が洞察節に流入しない（候補原文のみ）/ 違反時に advise 全体が壊れず縮退する / 候補0本日は節・契約とも不在 / 既存契約フィールドの検証が1つも弱まらない。

## §T2 朝決算カード — 新マーカー `kaizenlog:decision`

**目的**: 判定確定は朝（backfill）なのに決定を記入する器がない。実運用 done 0/26 件の「読むが動かない」構造への直接攻撃。チェックの意味を「完了報告」から「意思決定」へ変える。決定はすべて決定論（LLM 不関与）。

### T2-1 朝の描画（cmd_morning に追加）

`backfill_verdicts` の結果を使い、morning が当日ノートへ描画:

```markdown
## ⚖ 今日の意思決定（1件・朝に確定）
昨日の確定判定: KZN-20260801-001 ❌FAIL（ai_retry_chains 実測 4 / 目標 <= 0）

**問い: KZN-20260801-001 を今日も実行するか**
- [ ] 採用（今日実行する）
- [ ] 見送り｜理由: ＿＿
- [ ] 別案でいく｜内容: ＿＿
```

- 「昨日の確定判定」: 前日 `verdict_date` の confirmed 判定（backfill 結果 + suggestions.jsonl）。表示は既存の判定表記（✅/❌ + 実測/目標）を流用。
- 「問い」の対象: 朝の📌1件（`render_actions_section(max_candidates=1)` と同じ選定結果の KZN ID）。ACTIONS 区間とは別に、その1件を実行するか否かの意思決定として提示する。
- 確定判定も📌候補も無い日は区間を出さない。
- SECTION_ORDER 位置: `RESUME_MARKER` の後・`GOAL_MARKER` の前。

### T2-2 夜の読み戻しと決算（cmd_generate に追加）

夜の generate が当日ノートの decision 区間を読み戻し:

1. **チェックのパース**: 3択のうち `- [x]` の行を専用パーサで読む（`update_statuses_from_note` は ACTIONS/KZN status 用なので**流用しない**。decision は status に触らない独立記録）。見送り理由・別案内容は `_SKIP_REASON_RE` と同記法（`｜理由: …` / `｜内容: …`）で抽出。未記入（全て `- [ ]`）は「未決定」として扱い、台帳追記しない。
2. **台帳追記**: `MemoryEntry` にオプションフィールド `decision: dict | None = None` を追加（`{"choice": "adopt|skip|alternative", "reason": str|None, "date": "YYYY-MM-DD"}`）。旧レコードのキー欠落は None（verdict_stage :69-75 と同型の耐性）。同一ID後勝ちマージの挙動を変えない。
3. **決算の追記描画**: 同区間を「朝の内容（チェック状態・手書き理由を含む）を読み戻して保持したまま」再構成し、末尾に決算を足して write_section:

```markdown
### ⚖ 今日の決算
- 朝の決定: 採用
- 観測: ai_retry_chains 当日実測 1（7日中央値 2）。決定との因果は断定しません。
- 判定への接続: 明朝の backfill で確定します
```

- 観測行の実測値は `parse_pass_condition`（verdict.py:76-105）で問い対象アクションの metric を取り、当日 stats から決定論算出（既存の判定ロジックの読み出しを流用。算出不能なら「観測: 未判定（分母不足）」等の既存語彙で正直に）。
- **手書き保持が最優先**: チェック・理由・別案の手書きテキストが generate 再実行で1バイトも失われないこと（reflect と同じ読み戻し保持方式・冪等）。

### T2-3 見送り理由の活用（最小限）

`decision.choice == "skip"` が直近7日で2回以上ある KZN ID は、朝の「問い」の対象から外して次点候補を出す（候補選定の文脈フィルタ。指標や提案自体は殺さない — 提案書 §柱1b の設計判断どおり）。実装は morning の対象選定に1条件足すだけに留める。

**受け入れ条件**: 決算追記後も朝のチェック・手書きが完全保持 / 未記入日は台帳に何も書かれない / decision フィールド追加で旧 JSONL の読み込み・後勝ちマージ・既存判定フローが不変 / skip 2回フィルタが status を一切変更しない / 区間なし条件（判定・候補ゼロ）。
