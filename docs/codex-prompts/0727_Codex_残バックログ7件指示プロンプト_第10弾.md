## §H1 スキル化の効果測定 — プロンプト資産化の複利を実測する（旧B3）

`src/kaizenlog/promptmine.py`、`experiments.py`、`cli.py`、`skills/kaizen-autopilot/SKILL.md`

- **背景**: `/kaizen-autopilot` が頻出依頼をスキル化しても、その後「同じ生依頼が減ったか」を誰も測っていない。作りっぱなしのスキルは資産ではない
- **実装**:
  1. `promptmine.py` に `count_cluster_matches(prompts, representative, similarity=0.6) -> int` を追加（`normalize` 済み代表文との SequenceMatcher 比較。クラスタリングと同じ 0.6）
  2. 実験ノートの frontmatter に任意フィールド `cluster_rep`（正規化済み代表文）を追加し、`Experiment` dataclass に取り込む
  3. 新メトリクス `prompt_cluster:<slug>`: `cmd_generate` の実験計測ループで、`metric` がこのプレフィックスかつ `cluster_rep` があるときは、当日の `scan_user_prompts` 結果（リトライ連鎖用に取得済み）から `count_cluster_matches` で日次件数を算出する（`compute_metric` を汚さず、ループ側で分岐してよい）。`cluster_rep` 欠落時は計測不能としてスキップ
  4. `METRIC_DESCRIPTIONS` に `prompt_cluster:<slug>` を追記（説明: 指定クラスタに類似する生依頼の件数/日。要 cluster_rep）
  5. `kaizen-autopilot` SKILL.md 手順5を更新: クラスタからスキルを生成したら、`metric: prompt_cluster:<slug>` / `cluster_rep: <正規化代表文>` / `target: "<= 0"` / 14日 の効果測定実験を必ず起票する（正規化は `kaizenlog prompts` の表示から採る旨を明記。機密を含む生文をそのまま書かない注意も記載）
  6. `kaizenlog prompts` レポート: 追跡中の `prompt_cluster` 実験に対応するクラスタへ「📉 追跡中: <実験タイトル>」を付記
- **テスト**: count_cluster_matches の類似境界 / cluster_rep 付き実験の日次計測 / cluster_rep 欠落でスキップ / prompts レポートの付記

## §H5 失敗通知が通知自体の失敗で消える（notify.py）

`src/kaizenlog/notify.py:28-54`

- **問題**: `message.replace("'", "''")[:200]` とエスケープ→切り詰めの順のため、200文字境界が二重化した `''` の間に落ちると PowerShell リテラルが壊れ、失敗トーストが無音で消える。さらに `subprocess.run` の returncode を見ずに True を返すため検知不能
- **修正**: 切り詰めをエスケープ**前**に行う（title の `[:80]` も同様）。returncode 非0 のときは False を返し、呼び出し元でコンソールに1行警告（通知失敗で本処理は止めない）
- **テスト**: 199〜201文字境界に `'` を置いたケースでリテラルが壊れないこと（生成コマンド文字列の検証）/ returncode 非0 で False

## §H6 LLM全滅時の最悪所要がタスクの ExecutionTimeLimit を超える

`scripts/register-task.ps1`、`src/kaizenlog/cli.py`（run 経路）

- **問題**: 既定設定の最悪ケース（主バックエンド 600s×3回＋リトライ待機、フォールバック側も同様）で advise 1回 ≒ 61分。夜間 run は retro-advise ＋ 当日 advise で最悪2倍になり得るが、タスクの ExecutionTimeLimit が1時間のため途中で強制 kill され、log_run も失敗通知も残らない（「静かな故障」防止設計の破れ）
- **修正**: ExecutionTimeLimit を3時間に引き上げ（日次・朝タスク両方。最悪所要の見積もりをスクリプトコメントに明記）。あわせて run 経路の retro-advise に「主 advise を優先する」ガード: retro-advise が AdvisorError で失敗したら即座に諦めて当日処理へ進む（リトライは generate_text 内部に任せ、catch_up 側で追加リトライしない）ことをコメントで明文化
- **テスト**: なし（PowerShell）。cli 側は既存の失敗非伝播テストがあれば流用確認のみ

## §H7 夜間 run の retro-advise 直後に実行機会ゼロの提案が即時判定される

`src/kaizenlog/cli.py`（run 経路と cmd_generate の判定呼び出し）

- **問題**: 夜間 run は `catch_up_yesterday`（昨日日付の KZN を新規作成）→ `cmd_generate(today)`（proposal_day=昨日を判定）の順で走るため、数秒前に生まれてユーザーが一度も見ていないアクションに即 pass/fail が付き、PASS率と朝通知を汚染する
- **修正**: `catch_up_yesterday` が retro-advise で新規作成した KZN ID の集合を返し、同一プロセス内の直後の `cmd_generate` 判定でそれらを除外する（verdict は None のまま残る。「判定は実行機会があった提案のみ」という原則をコメントに明記）。朝の `kaizenlog morning` 経由の retro-advise は当日実行前なので除外不要（その日の夜に通常判定される）
- **テスト**: run 相当の順序で retro-advise 由来エントリに verdict が付かないこと / morning 経由では翌晩に通常判定されること
