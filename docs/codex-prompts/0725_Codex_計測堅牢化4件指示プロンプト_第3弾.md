## §A4 実験 baseline の汚染修正

**問題**: baseline は「実験開始後の最初の実測値」（`experiments.record_measurement`）＝介入開始後の値になるため、効果が系統的に過小評価される。

1. `src/kaizenlog/experiments.py` に `metric_from_stats(metric: str, stats: dict) -> float | None` を追加
   - 保存済み日次統計 JSON（`stats.write_stats` が書く形式を確認して実装）から指標値を復元する
   - 対応: `context_switches` / `total_active_minutes` / `ai_activity_blocks`・`ai_sessions` / `ai_cc_sessions`（ai.sessions）/ `ai_fragmented_sessions`（ai.fragmented）/ `ai_tool_errors` / `ai_interruptions` / `category_minutes:<名>`（by_category）/ `site_minutes:<域>`（by_site）/ input 系（保存されていれば）
   - 統計に保存されていない指標（例: ai_avg_turns が復元不能な場合）は None を返し、対応表をコメントに明記
2. `create_experiment(...)` に `baseline: float | None = None` 引数を追加。指定時は frontmatter の `baseline:` に `{value:g}` を書き込む
3. 起票側で開始前ベースラインを算出して渡す:
   - `cli.py` の `experiment new` ハンドラと `cmd_block` の実験起票ループで、`load_stats(cfg.stats_path, days=7, end_day=起票日の前日)` から `metric_from_stats` で日別値を集め、**3日以上**あれば中央値を baseline として渡す。不足時は従来どおり未設定
   - コンソール出力例: `📐 baseline: 直近5日の中央値 42（開始前実測）`
4. `record_measurement` の「baseline 未設定なら最初の実測で埋める」フォールバックは維持（手書きノート互換）

## §A5 adopted 実験の定着監視（退行検知）

**問題**: `status: adopted` になった実験は計測対象から外れ（`cmd_generate` は running のみ計測、`render_experiments_context` も running/expired のみ）、習慣の退行を誰も検知しない。

1. `cmd_generate` の実験計測ループ: `adopted` も計測対象に加える。ただし無期限に増やさないため、**deadline から30日以内**の adopted のみ（deadline 無しの adopted は対象外）。定数 `_ADOPTED_MONITOR_DAYS = 30` を experiments.py に置く
2. `src/kaizenlog/experiments.py` に `detect_regressions(experiments, window=7) -> list[Experiment]` を追加
   - adopted かつ直近 `window` 日以内の実測が3点以上あり、その**過半数が目標未達**なら退行
3. `cmd_generate` で計測後に退行を検知したら出力: `⚠️ 退行検知: 「タイトル」が採用後に目標未達（直近7日でx/y日未達）。再実験を検討してください`
4. `skills/weekly-kaizen/SKILL.md` 手順4b に追記: adopted 実験が退行条件（直近7日の実測の過半数が未達）を満たす場合、レビューの「今週の実験結果」に退行として記載し、`status: running` に戻して deadline を +14日する（frontmatter の書き換えは weekly スキルの責務）
5. `render_experiments_context` は現状維持（adopted を LLM コンテキストに常時流し込まない。退行時は weekly が running に戻すことで自然に復帰する）

## §L2 出力契約失敗時の縮退保存

**問題**: 修復1回後も契約違反だと `AdviceContractError` で advise が失敗し、その夜はノートに何も残らない（静かな失敗）。

1. `src/kaizenlog/advisor.py` `generate_advice`: 修復を試みる際にコンソールへ出力
   `⚠️ 出力契約違反を検出、1回だけ修復を試みます: <違反の先頭1件>`
2. `src/kaizenlog/cli.py` `cmd_advise`: `generate_advice` 呼び出しを `except AdviceContractError` で捕捉し、縮退セクションを保存してから**例外を再送出**する（実行ログ・失敗通知の既存経路は維持）
   - 縮退セクション（ADVICE_MARKER 区間へ upsert）:
     ```markdown
     ## 🚀 Kaizen（AIからの改善提案）

     ⚠️ 本日は提案の生成が出力契約を満たさず、保存できませんでした（詳細は `kaizenlog status`）。
     以下は当日の確定事実サマリーです。

     <evidence_ctx.markdown>
     ```
   - チェックボックス・KZN ID を含めない（Memory 走査と干渉させない）
   - evidence_ctx が None の場合は事実サマリー部を省略
3. 翌日以降の正常な advise が同区間を上書きすることを確認（既存 upsert の挙動で自然に満たされるはず）

## §L3 user_turns へのスラッシュコマンド混入修正

**問題**: `aiwork.scan_user_prompts` は `<command-...>` ラッパーを除外するが、`scan_sessions`（`_update_session`）の user_turns カウントは除外しておらず、往復数と `ai_avg_turns` 実験値が水増しされる。

1. `src/kaizenlog/aiwork.py` にモジュールレベルの `_is_command_wrapper(text: str) -> bool` を抽出（現在 scan_user_prompts 内にあるインライン判定: `text.startswith("<") and ("command-" in text[:40] or "local-command" in text[:40])`）
2. `_update_session` の user テキスト分岐で、`_is_command_wrapper(joined)` なら user_turns に数えない（interruption 判定より後、カウントより前）
3. `scan_user_prompts` も同じヘルパーを使うよう置き換え
4. コマンドラッパーのみのセッションは user_turns 0 となり、既存の最終フィルタ（user_turns > 0 or interruptions > 0）で自然に除外されることをテストで固定
