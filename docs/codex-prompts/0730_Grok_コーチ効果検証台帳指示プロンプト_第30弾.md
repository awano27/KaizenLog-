## Phase 1 — §A: 台帳と機械判定

### §A1 台帳モジュール(新規 `src/kaizenlog/coachledger.py`)

- `COACH_LEDGER = "coach_ledger.jsonl"`(`<memory_path>/` 直下)
- `CoachLedgerEntry` dataclass: `id`(形式 `CCH-YYYYMMDD-NNN`)・`applied_on`・`proposal_file`(memory_path からの相対)・`targets: list[str]`・`evidence: list`・`watch_metrics: list[str]`・`status`(`watching|pass|fail|rolled_back|superseded|unmeasurable`)・`verdict_date: str|None`・`verdict_detail: str|None`
- 読み込みは **last-wins**(promptledger.py:46-94 の `by_id` パターンを踏襲)、書き込みは append-only(decay.py:93-101 の `open(..., "a")` パターン)
- ID採番は `next_prm_id`(promptledger.py:109)と同方式の `next_cch_id`

### §A2 適用時記録とメトリクス登録

1. **watch metrics の決定論導出**: 固定セット `["ai_retry_chains", "ai_tool_errors", "loop_tax_episodes"]`(コーチの目的=摩擦削減に対応)。evidence の fact_id による追加は本弾では行わない(将来拡張)
2. **メトリクス登録**: 上記3名が `METRIC_DESCRIPTIONS`(experiments.py:31-53)と `metric_from_stats`(experiments.py:189)に無ければ追加する(**既存名があれば再利用し、重複追加しない**。読み取り元: stats v2 の `ai.retry_chains`(stats.py:185)・`ai.tool_errors`(stats.py:182)・`ai.loop_tax.episode_count`(stats.py:208-211、loop_tax欠落日は None を返す=測定不能))。登録すると `verdict.is_known_metric`(verdict.py:44)経由で KZN 機械PASS構文でも使えるようになる(副次効果、テストで確認)
3. **`apply_proposal` 後の記録**: `cmd_coach` の `--apply` 成功時(cli.py:1488-1503)に台帳へ追記: applied_on=当日・targets=書き込み先・evidence=提案から復元(`_parse_proposal_text`)・status=watching
4. **上書きの正直な処理**: 適用時に status=watching の既存エントリがあれば、そのエントリを `superseded` に更新(last-wins追記)。マーカー区間置換により旧提案の効果測定は継続不能なため

### §A3 夜間機械判定(決定論)

- `cmd_generate` の decay ブロック(cli.py:362-382)の**直後**に同型の try ブロックを追加し、`judge_coach_entries(cfg, as_of=day)` を呼ぶ
- 判定対象: status=watching かつ `as_of >= applied_on + 7日` のエントリ(一発判定、再判定なし)
- 判定方法(compute_abtest_effect の正規化機構を流用、experiments.py:806-865 参照):
  - 各 watch metric m について、適用後7日間の各日 `v = metric_from_stats(m, s)`、`wb = weekday_baseline(m, d, pre_stats)`(pre_stats=適用日前28日、experiments.py:323)で無次元指数 `v/wb*100` を計算
  - **fail-closed**: baseline 不足(wb None/0)の日はその日を捨て、metric の測定可能日が3日未満ならその metric は判定しない。全 metric が判定不能なら status=`unmeasurable`(理由を verdict_detail に記録)
  - metric 単位: 中央値指数 <= 100 で PASS、> 100 で FAIL
  - **総合**: 測定可能 metric の過半数が FAIL なら総合 FAIL、それ以外は PASS(detect_regressions の過半数方式に合わせる)
- 判定結果を台帳に追記(status=pass/fail、verdict_date、verdict_detail=`"ai_retry_chains 中央値118 / loop_tax_episodes 中央値92"` 形式・redact不要な構造化文字列のみだが念のため redactor 通過)
- FAIL 時は §B1 のロールバック提案を自動生成し、`_notify(cfg, ...)`(cli.py:167。生 notify 禁止)で1回通知

## Phase 2 — §B: ロールバック提案(承認ゲート)

### §B1 生成

- FAIL 判定時、`<memory_path>/coach/<date>-rollback-<CCH-id>.md` を生成: frontmatter `kind: rollback`・`ledger_id: CCH-...`・`applied: false`、本文に除去対象の append_md(提案ファイルから復元)と判定根拠
- 既に同一 ledger_id のロールバック提案が存在すれば再生成しない

### §B2 適用

- `coach --apply <rollback-file>` は frontmatter `kind: rollback` を検出したら除去モードで動作:
  - 各 target の COACH_MARKER 区間の現内容が記録済み append_md と**一致する場合のみ**、区間を空にする(upsert_section で空文字列に置換)
  - 一致しない(別の提案で上書き済み)場合は `AdvisorError("対象区間は別の提案で上書き済みです")` で**ゼロ書き込み**拒否
  - 成功時: rollback ファイルの applied を true 化(二重適用拒否は既存 coach.py:402-405 と同方式)+ 台帳 status=rolled_back を追記
- 事前全検証→書き込み→例外時全ロールバックは `_validate_proposal_for_apply` / `apply_proposal`(coach.py:377-478)の既存構造を拡張して実現(並行実装の新関数で分岐してもよいが、ゼロ書き込み保証は同水準)
