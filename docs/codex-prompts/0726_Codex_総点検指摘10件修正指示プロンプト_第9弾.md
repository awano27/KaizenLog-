## §G1 [High] カスタム system_prompt の出力が render_reader_advice で無言破棄される

`src/kaizenlog/cli.py:569`

- **問題**: `requires_daily_contract` が偽のプロンプト（weekly_review / ai_work_deep_review / 自作ファイル）では `generate_advice` が出力を素通しする設計（advisor.py:824-826 と docstring が明言）なのに、`cmd_advise` は無条件に `render_reader_advice(advice_md, evidence_ctx)` を適用する。この関数は「### 明日の最小アクション」抽出＋evidence 定型文で**全文を再構成**するため、日次形式でないカスタム出力は本文が丸ごと消え、「✅ 改善提案を書き込みました」と成功表示される
- **修正**: cli.py:569 を `requires_daily_contract(cfg.llm)` でゲートし、非日次契約プロンプトの出力はそのまま保存する
- **テスト**: `tests/test_hardening_round3.py:244` の `render_reader_advice` を identity にする monkeypatch がこの経路を隠している。モックを外すか、非日次プロンプトでカスタム本文がノートに残る実経路テストを追加

## §G2 [High] evidence ゲート付き契約チェックが「renderer bug」に誤分類され、修復と縮退保存を両方バイパスする

`src/kaizenlog/advice_format.py:414-425`、`src/kaizenlog/advisor.py:500-526`

- **問題**: `advice_contract_errors` にだけ存在する evidence ゲート付き内容チェック（『通知』禁止・previous_day_available 偽時の『前日』・AI依頼最適化・watcher）は JSON 層の `validate_advice` にも `_semantic_contract_errors` にも無いため、レンダ後インバリアントで初検出 → 部分集合判定から漏れて `AdvisorError("renderer bug")` になり、修復1回も L2 縮退保存も走らず夜間 advise が全落ちする。さらにレンダラ自身が付与する指標ラベル（例『Claude Codeセッションの平均往復数』の「Claude」「往復」）がこれらのチェックを誤爆させる。plan_review 内の `#` 開始行・`- [ ]`・コードフェンスも同様に renderer bug 化する
- **修正（4点セット）**:
  1. evidence ゲート付き内容チェックを `validate_advice`（JSON 層、注記付与前の生フィールド）にミラーする
  2. `advice_contract_errors` のアクション行スキャンでは PASS 注記部分を `strip_pass_annotation` で除去してから内容チェックする（レンダラ由来ラベルの誤爆防止）
  3. インバリアントの分類で、evidence ゲート付き内容チェックのエラーは「意味系」として扱い `AdviceContractError` に送る（構造系のみ renderer bug）
  4. plan_review の行頭 `#` / `- [` / ` ``` ` を JSON 層で違反にする
- **テスト**: `test_advice_format.py:160-191` は分類ロジックの両側をモックしており実分類を検査していない。モック無しで (a) 『通知』を含む action が修復対象になる、(b) `pass="ai_avg_turns <= 3"` のレンダラ注記が誤爆しない、(c) 構造破壊のみ renderer bug、の3系統を追加

## §G3 [High] privacy_safe ＋ redact_patterns の組合せが LLM 呼び出し前に必ず失敗する

`src/kaizenlog/prompts/privacy_safe.md:37`、`src/kaizenlog/advisor.py:754-771`

- **問題**: `_assert_redaction_preserves_daily_protocol` はシステムプロンプト内に `"proposals"` 等の**引用符付きキー**を要求するが、privacy_safe.md はバッククォート表記しか含まないため、`system_prompt = "privacy_safe"` かつ redact_patterns が1件でもあると、無害なパターンでも常に AdvisorError（しかもユーザーの設定を誤って非難する文言）。プライバシー重視ユーザーの最自然な組合せが全断する
- **修正**: privacy_safe.md に daily_advisor.md と同様の JSON スキーマ例示ブロック（引用符付きキー含む）を追加する。検証キーの緩和ではなくプロンプト側を直す（検証の意図＝マスクがスキーマ例を壊していないかの確認、を保つため）
- **テスト**: privacy_safe ＋ redactor で prepare_advice_request が成功する / 過剰マスクでキーが消えた場合は従来どおり失敗する

## §G4 [Medium] 📌転記セクションでのチェックが scan_days の穴で検出されない

`src/kaizenlog/cli.py:480-486`

- **問題**: done 検出の走査対象は `{当日} ∪ {未完了エントリの提案日}` のみ。「KZNチェックボックスは提案日のノートにしか存在しない」というコメント前提は A2 の転記導入後は虚偽で、中間日ノートの📌でチェックすると（その日に自分の open 提案が無い場合）永久に done にならず、消化率が過小評価され適応投与が誤発動しうる
- **修正**: scan_days に「直近7日」（転記ウィンドウと同じ幅。定数を共有）を常に加える。コメントも実態に合わせて更新
- **テスト**: 中間日ノートの転記セクションだけでチェックされたアクションが done 化される

## §G5 [Medium] 既存ユーザーが setup を再実行しても朝タスクが登録できない

`src/kaizenlog/setup.py:381-384`、`src/kaizenlog/setup_detect.py:125`

- **問題**: Phase 6 は `KaizenLog Daily` の存在だけで「登録済み」としてフェーズ全体をスキップし、`KaizenLog Morning` の有無を見ない。朝タスク機能導入前にセットアップ済みのユーザーは `--force` でも朝タスクを追加できない
- **修正**: Daily / Morning を個別に判定し、欠けている方だけ登録を提案する。`is_task_registered` にタスク名引数を追加
- **テスト**: Daily 登録済み・Morning 未登録の検出結果で Morning の登録が提案される（schtasks はモック）

## §G6 [Medium] LLM が PASS に自前の括弧注記を付けると二重注記になり自動判定が無音で欠落

`src/kaizenlog/advice_format.py:402`、`src/kaizenlog/verdict.py`（strip_pass_annotation）

- **問題**: LLM が `pass="context_switches <= 40（コンテキストスイッチ回数）"` を返すと検証は通過（strip してから機械構文判定）するが、レンダラが注記を再付与して二重括弧になり、`strip_pass_annotation` は1組しか剥がさないため `parse_pass_condition` が None → 翌晩の判定が黙ってスキップ。SKILL.md の例が注記付き PASS を示しており、モデルが模倣する現実的リスクがある
- **修正（両方）**: レンダラは `strip_pass_annotation(pass_raw)` に正規化してから注記を付与する。`strip_pass_annotation` は末尾の括弧ペアが無くなるまでループで剥がす（防御の二重化）
- **テスト**: 注記付き pass 入力 → レンダ結果が単一注記 → parse_pass_condition が解析できるラウンドトリップ

## §G7 [Medium] assign_action_ids の同日再実行で同一 KZN ID が2行に付与されうる

`src/kaizenlog/memory.py:150-165`

- **問題**: テキスト一致再利用パスが used_ids を確認しないため、新アクション順が [新規C, 既存A] のとき C が汎用パスで E1 を消費した後、A がテキスト一致で同じ E1 の ID を再取得し、ノートに同一 ID の行が2本できる（done 検出・判定の対象がズレる）
- **修正**: 全行のテキスト一致解決を先に行ってから汎用再利用パスを走らせる（または一致パスでも used_ids を除外）
- **テスト**: 上記の順序で ID 重複が起きないこと

## §G8 [Medium] superseded エントリが機械判定・統計・朝通知を汚染する

`src/kaizenlog/verdict.py:145-151`、`src/kaizenlog/memory.py:249-261`

- **問題**: `judge_entries` は date のみでフィルタし、同日再 advise で撤回された `status: superseded` にも verdict を付与する。`compute_action_stats` の分母（proposed）にも superseded が含まれ、消化率・PASS率・朝トーストの「昨日の判定」が水増しされる
- **修正**: judge_entries は `status in ("proposed", "done")` のみ判定。compute_action_stats と朝通知の集計から superseded を除外
- **テスト**: superseded を含むエントリ集合で、判定・消化率分母・トースト集計のいずれにも入らないこと

## §G9 [Medium] register-task.ps1 が失敗しても成功メッセージと exit 0 を返す

`scripts/register-task.ps1`、`src/kaizenlog/setup.py:230-233`、`src/kaizenlog/cli.py`（--time / --morning-time）

- **問題**: `$ErrorActionPreference` 未設定・try/catch 無しのため、不正時刻（"25:00" 等）で登録に失敗しても「登録しました」と表示して exit 0。ウィザードは returncode だけ見るので偽の成功を報告し、夜間実行が一度も走らない静かな故障になる
- **修正**: スクリプト冒頭に `$ErrorActionPreference = 'Stop'`、登録処理を try/catch で包み失敗時は exit 1。cli / setup 側の `--time` / `--morning-time` に HH:MM 形式検証を追加
- **テスト**: 時刻書式検証の単体テスト（PowerShell 実行はしない）

## §G10 [Medium] 朝タスク追加の再実行で既存日次タスクの時刻・作業フォルダが黙って既定値に戻る

`scripts/register-task.ps1:50-57`

- **問題**: 日次タスクの登録が無条件 `-Force` 上書きのため、`-MorningTime` だけ指定して再実行すると日次が 21:30 と現カレントディレクトリに巻き戻る（カレント依存の設定解決事故を再導入）
- **修正**: 日次タスクは「`-Time` が明示された場合」または「未登録の場合」のみ登録する。既存があり `-Time` 未指定なら現状維持し、その旨を表示。朝タスク側も同じ規則
- **テスト**: なし（PowerShell）。スクリプト内コメントに規則を明記
