## 背景（レビューで判明した本質的欠落）

`insight_selection_errors`（advice_format.py:651）は**関数として書かれただけで `validate_advice` / `_validate_advice_raise` から一度も呼ばれていない**。そのため LLM が存在しない候補ID（C99）や数字入り connector を返しても契約違反が発生せず、修復ループ（advisor.py:899 の文言）は到達不能、実挙動は常に render 側の暗黙縮退のみになる。さらに出力 JSON スキーマに `insight_selection` が記載されていないため、実 LLM がこのフィールドを生成する見込みが薄く、機能全体が「常時縮退＝上位2本固定」で固定化する。テストは `insight_selection_errors` を直接呼んで検証しており、この未配線を検出できていない。

## §U1 契約検証の本番経路への統合（最優先）

`insight_selection_errors` を `_validate_advice_raise`（advice_format.py:377）の検証フローに統合し、違反が実際に `AdviceContractError` として送出されるようにする。

- 候補0本日はフィールド非要求（既存 :659-662 の挙動を維持）。
- 修復ループ（`_contract_repair_prompt` advisor.py:867）が insight 違反でも回ることを確認する。
- 縮退（違反が修復されなかった場合に候補上位2本を描画）の既存挙動は変えない。

**受け入れ条件**: `validate_advice` / advise の本番検証経路を通して (a) 存在しない candidate_id、(b) 数字入り connector、(c) 3件以上の選定、がそれぞれ `AdviceContractError` になるテスト（`insight_selection_errors` の直呼びではなく **validate 経由**で検証）。既存の直呼びテストは残してよい。

## §U4 決算追記の冪等化（skip フィルタ誤発火の防止）

`cli.py:508-516` が generate のたびに decision レコードを無条件 `append_entries` しており、同日 generate 2回で台帳に重複行が入る。さらに `skip_counts_last_days`（decision.py:1722-1745）は**行数**を数えるため、重複で skip カウントが水増しされ §T2-3 フィルタが誤発火する。

修正（両方）:

1. **追記ガード**: 追記前に台帳を読み、同一 KZN ID・同一 `decision.date` の decision が既に記録済み（後勝ち解決後）なら追記しない。
2. **カウントの一意化**: `skip_counts_last_days` を「ID×日付で一意化してから数える」実装に変え、既に混入した重複行にも耐性を持たせる（台帳の既存行は書き換えない。読み出し側で吸収する）。

**受け入れ条件**: 同日 generate 3回実行後も decision レコードが1件・skip カウントが1のテスト / 既に重複行がある台帳フィクスチャでもカウントが正しいテスト。
