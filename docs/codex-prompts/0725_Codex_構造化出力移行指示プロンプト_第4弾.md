対象リポジトリ: `C:\develop\KaizenLog\KaizenLog-`（Python / pytest）

**前提: 第1弾〜第3弾適用済み。** 特に第1弾の機械構文 PASS 検証（is_known_metric）と第3弾 L2 の縮退保存が存在すること。未適用なら中断して報告する。

## 背景と目的

現在、LLM が出力した Markdown を `advisor.advice_contract_errors` の正規表現群（約200行）で検証している。見出し重複・チェックボックス数・提案とアクションの1対1対応などの違反は「検証して弾く」のではなく「構造で作れなくする」方が堅牢。日次提案（daily_advisor / privacy_safe）を **LLM は JSON を返し、Markdown は KaizenLog が決定論的にレンダリングする**方式へ移行する。

**不変条件（最重要）**: レンダリング後の Markdown は現行フォーマットと完全互換であること。下流の `memory.assign_action_ids`（KZN ID 付与）、第1弾の `verdict.parse_pass_condition`（PASS 解析）、`update_statuses_from_note`（done 検出）が**無変更で**動き続けること。

## §L1-1 新モジュール `src/kaizenlog/advice_format.py`

### スキーマ（dict ベースで検証。外部ライブラリ追加禁止）

```json
{
  "plan_review": "計画と実績の評価（1〜3行、改行可）| null（計画が無い場合）",
  "proposals": [
    {"fact_ids": ["F2"], "interpretation": "解釈", "proposal": "提案", "next_metric": "翌日見る指標"}
  ],
  "actions": [
    {"fact_ids": ["F2"], "action": "15分以内に始める行動", "pass": "context_switches <= 40", "fail": "41回以上"}
  ],
  "ai_review": [
    {"fact_ids": ["F5"], "text": "AI作業の評価・改善"}
  ]
}
```

### `parse_advice_json(text: str) -> dict`（例外 `AdviceContractError`）

- 前後の ```json / ``` フェンス、説明文の混入を許容: 最初の `{` から対応する最後の `}` までを抽出してから `json.loads`
- パース失敗・トップレベルが dict でない場合はエラー（修復対象）

### `validate_advice(data, evidence: AdviceEvidence) -> list[str]`

構造検証（旧契約と同等の意味を JSON 上で）:

- proposals / actions: 1〜3件かつ**同数**、ai_review: 1〜2件
- 各 fact_ids: 非空、`evidence.fact_ids` の部分集合。actions[i] と proposals[i] は少なくとも1つ根拠 ID を共有
- ai_review の fact_ids に F4 または F5 を含む（evidence に存在する場合）
- action / pass / fail / next_metric / interpretation / proposal / text: 非空文字列、改行禁止（plan_review のみ改行可・3行以内）
- pass が機械構文らしい（`^\S+\s*(<=|>=|<|>|==?)\s*[\d.]+$`）のに `is_known_metric` 偽なら違反（第1弾 A1-4 と同基準。判定関数を verdict.py から import）
- pass / fail に数値を含む（旧契約の数値条件必須を維持）
- **数値再掲の禁止（フィールド分離で置換）**: `interpretation` と `ai_review.text` は数字を含んではならない（観測値の再掲防止）。`proposal` / `action` / `pass` / `fail` / `next_metric` は数字可（旧ルールの「提案文に一切数字を書けない」窮屈さを解消）
- テキストに `KZN-\d{8}` を含まない、マーカー文字列 `<!--` を含まない

意味検証: 既存の `_semantic_contract_errors` を再利用する。全テキストフィールドを結合した文字列に対して適用（娯楽断定・AI往復数捏造・ブロック→会話数変換の各ガード。日本語フレーズ前提である旨のコメントを維持）。

### `render_advice_markdown(data, evidence) -> str`

現行契約と同一構造の Markdown を決定論的に生成:

```markdown
### 計画と実績
（plan_review が null なら見出しごと省略）

### 今日の改善提案
1. [F2] {interpretation}。{proposal}。翌日見る指標: {next_metric}

### 明日の最小アクション
- [ ] [F2] {action}｜PASS: {pass}｜FAIL: {fail}

### AI作業の改善
- [F5] {text}
```

- fact_ids が複数なら `[F2] [F8]` と空白区切り（アクション行は先頭が `[F#] ` で始まること — 旧契約の正規表現 `^\[F\d+\]\s` 互換）
- レンダリング後に **`advice_contract_errors(rendered, evidence)` を内部インバリアントとして実行**し、違反があれば `AdvisorError("renderer bug: ...")`（レンダラのバグを LLM 修復ではなく即時失敗として検出する）

## §L1-2 `advisor.generate_advice` の書き換え

- `requires_daily_contract(cfg)` が真のパス: `generate_text` → `parse_advice_json` → `validate_advice` → 違反があれば修復プロンプト（従来同様1回。エラーリスト＋前回出力を渡し、**JSONだけを返すよう**指示）→ 再検証 → それでも違反なら `AdviceContractError`（第3弾 L2 の縮退保存が受ける）→ 合格なら `render_advice_markdown` して従来どおり `## 🚀 Kaizen（AIからの改善提案）` を前置して返す
- 偽のパス（weekly_review / ai_work_deep_review / 自作プロンプト）: 従来どおり素通し（変更なし）
- `advice_contract_errors` は削除しない（レンダラのインバリアント検証と daily-kaizen スキルの参照仕様として残す）。ただし public API の互換は維持
- `_contract_repair_prompt` は JSON 用の文言に更新
- `_assert_redaction_preserves_daily_protocol`: 必須見出しのチェックを「システムプロンプトに JSON キー名 `"proposals"` `"actions"` `"ai_review"` が残っていること」へ変更（F-ID 保全チェックは維持）

## §L1-3 プロンプトの書き換え

`prompts/daily_advisor.md` と `prompts/privacy_safe.md` の「出力契約」節を全面差し替え:

- 回答は **JSON オブジェクトのみ**（フェンス・前置き・後置きテキストなし）。スキーマとフィールドの意味、件数制約、fact_ids の対応規則を明記
- pass はできる限り機械構文（使用可能指標の一覧は第1弾 A1-5 のリストを維持）
- interpretation / text に観測数値を書かない（数値は F 本文が正）
- 分析ルール・測定限界の節（前半）は変更しない
- 文字数目安: 全テキストフィールド合計 400〜900字

`skills/daily-kaizen/SKILL.md` は Markdown 直書きのまま（エージェントがノートを直接編集する経路）。冒頭に「`kaizenlog advise` は JSON→レンダリング方式であり、本スキルの出力フォーマットはそのレンダリング結果と同一形式を保つこと」と1行追記のみ。

## §L1-4 テスト移行

- 既存の contract 系テスト（tests/test_advise_integration.py 等）: LLM モックの返り値を JSON に変更して同じシナリオを検証。**旧 Markdown を直接返すモックのテストは「JSON パース失敗→修復→縮退」の経路テストに転用**
- 新規 `tests/test_advice_format.py`:
  1. parse: 素の JSON / ```json フェンス付き / 前置きテキスト混入 / 壊れた JSON
  2. validate: 件数不一致、1対1違反、存在しない F-ID、F4/F5 欠落、未知指標の機械構文、interpretation に数字、action に改行、KZN 混入
  3. render: ゴールデン出力（固定 JSON → 期待 Markdown 完全一致）
  4. **ラウンドトリップ**: render 結果に対し (a) `advice_contract_errors` が空、(b) `assign_action_ids` が ID を付与できる、(c) 付与後の行から `parse_pass_condition` が機械構文を解析できる
  5. renderer インバリアント: 壊した render 出力で AdvisorError
- 修復経路: 1回目 JSON 違反 → 修復プロンプトに違反リストが含まれる → 2回目合格

`python -m pytest -q` 全件通過。作業完了時: 変更ファイル一覧・削除できた検証ロジックの行数・pytest 結果を報告すること。
