## Phase 1 — §A: `kaizenlog excavate`

**目的**: インストール直後、ディスクに既に眠る過去数ヶ月分の Claude Code / Codex / ブラウザAI ログを走査し、「過去90日で推定 $X(¥Y)を空転に支払いました」をゼロ日目に出す。

### §A1 コアスキャン(新規 `src/kaizenlog/excavate.py`)

- 入力期間: `--days N`(既定90)。`end = 今日`, `start = end - N日`
- **シングルパス必須**: 日毎に90回 rglob するのではなく、`available_adapters(cfg)`(aiwork.py:646)の各アダプタに対し `scan_sessions(start_dt, end_dt)` / `scan_user_prompts(start_dt, end_dt)` を**期間全体で1回だけ**呼ぶ(`collect_ai_telemetry`(aiwork.py:671)の期間広め呼び出しで可)。内部セッdata.は同関数の返り値3番目で除外済みであることを確認して使う
- 日別バケッティング(決定論): `detect_retry_chains`(aiwork.py:504)を期間全体のプロンプト列に1回適用し、各チェーンは**先頭プロンプトのローカル日付**に帰属させる。日別に `compute_loop_tax`(aiwork.py:832)相当の会計を出す(セッションは期間全体のリストを渡してトークン帰属)
- 集計(全て決定論・fail-closed): 期間合計のセッション数/出力トークン/推定コスト、空転税合計(エピソード数・浪費トークン・USD・`usd_jpy` 設定時は円)、最悪ループ日 Top5(日付・エピソード数・浪費トークン)、リトライ連鎖総数、ツールエラー総数、最悪エピソードの redact 済み抜粋1件。モデル不明が混在する日は既存の fail-closed 規約どおり総額「不明」
- **stats ファイルや日誌には一切書かない**(読み取り専用監査。過去日の stats 生成は既存 `backfill` の役割のまま)
- メモリ効率: JSONL は既存 scan の行ストリーミングに乗る。ファイル全体の一括 read を新設しない

### §A2 CLI と出力

- `kaizenlog excavate [--days 90] [--write] [--card]` を cli.py に追加(サブパーサ追加位置: cli.py:2110-2111 付近、dispatch は L2299 の backfill ブロック前後)
- 既定: 端末サマリのみ(セクション見出し+行、上記集計)
- `--write`: レポート Markdown を `<memory_path>/excavate/<YYYY-MM-DD>.md` に書く。本文は `<!-- kaizenlog:excavate:start/end -->` マーカー区間として `vault.upsert_section` で冪等生成(再実行で同一入力なら byte 同一)。書き込みは `atomic_write_text`
- `--card`: §A3 のSVGカードを `<memory_path>/cards/excavate-<YYYY-MM-DD>.svg` に出力
- アダプタが1つも無い場合: 「テレメトリソースが見つかりません(確認: claude_projects_dir / codex_sessions_dir)」で exit 1

### §A3 SVGカード(cardgen.py 拡張)

- `ExcavateCardData` dataclass + `render_excavate_svg` + `write_excavate_card` を cardgen.py に追加(既存 `_bar`(cardgen.py:24)を再利用可)。内容: 期間・空転税総額(USD/JPY)・エピソード数・最悪日。f-string 組み立てのみ、依存追加なし
- データ不足(セッション0件)時も「計測なし」デザインで必ず生成

### §A4 受け入れ条件

- `tests/test_round29_excavate.py`:
  - 合成JSONL(3日分・リトライ連鎖入り・internal混在)で日別バケット・internal除外・合計値を検証
  - モデル不明混在日の総額「不明」(fail-closed)
  - `--write` 2回実行で byte 同一(冪等)、`--card` のSVGが `xml.etree.ElementTree.fromstring` でパース可
  - redact_patterns 設定時に抜粋がマスクされる
  - stats ディレクトリと daily notes が実行前後で不変
- 確認コマンド: `./.venv/Scripts/python.exe -m kaizenlog.cli --config kaizenlog.toml excavate --days 30`

## Phase 2 — §B: 改善風化センチネル

**目的**: 「直したはずの問題」の復活を夜間 run で検知し、達成で物語を終わらせない。

### §B1 検知器3種(新規 `src/kaizenlog/decay.py`、全て決定論)

1. **skilled PRM 再発**: `load_prompt_ledger`(promptledger.py:46)の status=skilled かつ `marked_on` 有りエントリに対し、直近7日のユーザープロンプトを `find_matching_entry`(promptledger.py:130)で照合。**7日間で3回以上再発**したら風化
2. **採用実験の逆戻り**: 既存 `detect_regressions`(experiments.py:387、cmd_generate から cli.py:346 で呼出済み)の結果をそのまま風化イベントとして扱う(検知ロジックの再実装禁止)
3. **KZN PASS 後の悪化**: `load_entries`(memory.py:58)から status=done かつ verdict=pass かつ verdict_date が直近60日のエントリを対象に、`verdict.parse_pass_condition` で機械条件を復元し、直近7日の測定可能日で**過半数が条件違反**なら風化(測定不能日はスキップ。測定可能日が3日未満なら判定しない — fail-closed)

### §B2 風化台帳

- `<memory_path>/decay_ledger.jsonl` に append-only で記録: `{date, kind: "prm"|"experiment"|"kzn", ref_id, detail, evidence}`(detail/evidence は redact 済みテキストのみ)
- **クールダウン**: 同一 ref_id の風化イベントが30日以内に既にあれば追記しない(毎晩の重複記録防止)
- 読み込みヘルパー `load_decay_events(memory_dir, *, window_days)` を同モジュールに用意

### §B3 表面化(3経路)

1. **weekly**: `render_weekly_context`(weekly_context.py:105)は既に `memory_dir` を受けるので、内部で decay_ledger を読み「⚠️ 風化した改善」小節(直近7日のイベント、kind/ref_id/detail)を追加。イベント0件なら小節ごと省略。シグネチャ変更不要
2. **status**: `kaizenlog status` に「⚠️ 風化した改善: N件(直近7日)」を1行(0件なら非表示)
3. **advise 事実**: `advice_evidence.py` に **F17**(風化事実)を追加 — 直近7日の風化イベントを「[F17] 風化: KZN-... の metric が再悪化(N日中M日違反)」形式で列挙し、advisor が再提案 KZN を組み立てられる素材にする(**達成断定・自動再オープンはしない**。memory の status 変更は本弾のスコープ外)

### §B4 配線と受け入れ条件

- `cmd_generate` の stats 書き込み後に検知器を実行(夜間 run に乗る)。新規風化イベントが1件以上あれば `_notify(cfg, ...)`(cli.py:166。生 `notify` 直呼び禁止)で1回通知
- `tests/test_round29_decay.py`:
  - 3検知器それぞれの発火/非発火(閾値境界: PRM 2回は非発火・3回で発火、KZN 測定可能2日は判定しない)
  - クールダウン(同一 ref_id 30日以内は追記されない)
  - weekly 小節の出現/省略、status 行、F17 事実の生成
  - 通知はモックで1回のみ、decay_ledger の redact 適用
