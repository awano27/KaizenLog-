## §N1 [High] 非挑戦的PASSターゲットの入口ガード

`src/kaizenlog/advice_format.py`、`src/kaizenlog/advice_evidence.py`(F10帯の受け渡し)

**問題**: 入口検証は指標の実在・計測可否は見るが**目標値の挑戦性を見ない**。LLMがベースラインより大幅に緩い閾値(実測121に対し `<= 500`)を書くと恒久的に✅が並び、PASS率が無意味化する。

1. evidence が持つ指標のベースライン(F10帯 または 直近実測)を検証層に渡し、PASS閾値の妥当性を検査する:
   - `<=` 系(減らす目標): 閾値がベースラインの **1.2倍を超える**場合は契約違反(緩すぎ)。ベースライン未満は挑戦的なので常に可
   - `>=` 系(増やす目標): 閾値がベースラインの **0.8倍未満**の場合は契約違反
   - ベースラインが取得できない指標は検査しない(初日や新指標を弾かない。この理由をコメントに明記)
2. 修復プロンプトに「目標はベースライン(値を明示)より挑戦的に設定する」を含める

テスト: baseline=121 で `<= 500` が契約違反 / `<= 100` は通過 / `>= 2.5`(baseline 3.4)が通過・`>= 1` が違反 / baseline 無しは素通り。

## §N2 [High] 「今日の結論」の決定論的リッチ化

`src/kaizenlog/advisor.py`(render_reader_advice の結論部)、`src/kaizenlog/advice_evidence.py`

**問題**: 結論が合計分数の1文のみで、読者が最初に読む場所が最も情報が薄い。LLMに書かせると数字捏造リスクがあるため、**evidence からの決定論的文生成**でリッチ化する(設計原則「数字はコード」の範囲内)。

1. evidence の確定事実から最大3文を決定論で生成(存在するものだけ、優先順):
   - AI摩擦の集中: ツールエラー上位プロジェクトが全体の50%超を占める場合「ツールエラーN回中M回が『X』に集中」
   - カテゴリの特徴: 最大カテゴリと分数、エンタメが総時間の20%超なら言及(断定禁止の既存原則に従い「〜が記録されています」調)
   - 前日比: 前日statsがあれば合計時間・AIセッション数の増減を1つ
2. データが薄い日(合計120分未満等、既存の閾値に従う)は従来の1文のまま
3. 数字は evidence の確定事実のみ使用(LLM出力を混ぜない)。既存の禁止推論(エンタメ断定・会話数変換)を新文面でも守る

テスト: エラー集中日の文面 / 薄い日は従来文 / 前日stats有無の分岐 / 禁止推論を含まない。

## §N4 [Low] コスト行の意味明確化
