## §X2 [P0] 設定未作成の通常コマンドをfail-closedにする

対象:

- `src/kaizenlog/config.py`
- `src/kaizenlog/doctor.py`
- `src/kaizenlog/cli.py`
- `tests/test_setup_config.py`
- 新規 `tests/test_ux_round13.py`

### 問題

`Config.vault_dir = Path(".")` かつ `load_config()` が設定未検出時に既定値を返すため、初回ユーザーが `run` / `morning` 等を先に実行すると、CWD配下をボールト・統計・Memory・実行ログの保存先として扱い得る。`doctor` も設定なしを警告に留めるため、ActivityWatch等が偶然動いていれば「修正必須」にならない可能性がある。

### 必須修正

1. `setup` と `init-config` の特別扱い後、通常コマンドへ入る前に設定ファイルの存在を確定するCLIガードを追加する。
2. 設定ファイルが1件も見つからない場合:
   - `doctor` だけは診断を続ける。ただし「設定ファイルなし」を `Check.error` とし、終了コード1にする。
   - `doctor` はCWDを「書き込み可能なボールト」として正常判定しない。設定依存のVault、LLM、履歴、提案ヘルスは「設定作成後に確認」としてスキップし、設定なしでも意味のある環境確認だけを行う。
   - それ以外のコマンドは、外部接続・ファイル読み書き・ディレクトリ作成の前に終了コード2で止める。
   - stderr:

     ```text
     ❌ KaizenLogの設定がありません。まず `kaizenlog setup` を実行してください。
        診断だけ行う場合: `kaizenlog doctor`
     ```
3. 明示 `--config` と `KAIZENLOG_CONFIG` が欠落パスを指す既存fail-closedは維持する。
   - `main()` で `FileNotFoundError` を捕捉し、Python tracebackではなく安全な1〜2行の案内をstderrへ出す。
   - 通常コマンドは終了コード2。`doctor` は `Config()` を診断専用の仮値として続行し、欠落した正確な設定パスを設定エラーとして表示して終了コード1にする。
   - ドキュメントの例は、setup以外ではグローバルオプションがサブコマンドより前であることを示す: `kaizenlog --config PATH doctor`。
4. 既存のCWD `kaizenlog.toml` / `config.toml` は後方互換として「設定あり」に数える。`doctor` のAppData/XDG移行警告も維持する。
5. `load_config()` を直接利用するライブラリコードの既定値互換は、必要がなければ壊さない。CLI入口で安全境界を作る。
6. `--help` は設定なしでも従来どおり成功する。

### テスト

- 設定なしの `run` / `morning` / `today` / `done` / `status` が終了コード2で、ActivityWatch、LLM、Vault、Memory、runlogを呼ばない。
- 設定なしの `doctor` は診断文へ設定エラーを出し、終了コード1。
- 設定なしの `doctor` はCWDをボールトとして正常表示せず、設定依存チェックをスキップする。
- 欠落した明示 `--config` / `KAIZENLOG_CONFIG` はtracebackを出さず、通常コマンドはexit 2、`doctor` は診断結果つきexit 1。
- `setup --help` / `doctor --help` / top-level `--help` は設定なしで終了コード0。
- CWD設定、AppData/XDG設定、`KAIZENLOG_CONFIG`、明示 `--config` の既存優先順位は変わらない。
- テストは `tmp_path` とmonkeypatchだけを使い、実ホーム・実AppData・実CWDへ何も作らない。

## §X3 [P1] `morning` / `today` の副作用と部分成功を隠さない

対象:

- `src/kaizenlog/cli.py`
- `src/kaizenlog/runlog.py`
- `src/kaizenlog/doctor.py`
- `README.md`
- `docs/USAGE.md`
- `tests/test_ux_round8.py`
- `tests/test_round11.py`
- 新規 `tests/test_ux_round13.py`

### 問題

- `morning` は昨日の `generate` / `advise` と今日ノート更新を行い得るが、ヘルプだけではAW・LLM・書き込みの可能性が分からない。
- 追いつきの `generate` / `advise` が失敗しても、朝の一覧・通知を続けた後に `morning ok=True` が記録される。最後の成功だけ見たユーザーは復旧未完了を見失う。
- `today` は表示前にノートの `[x]` をMemoryへ追記同期するが、ヘルプでは表示専用に見える。

### 必須修正

1. `catch_up_yesterday` の戻り値を、`new_ids` だけでなく各ステップを表現する `CatchUpResult` へ変更する。
   - `generate`: `not-needed | succeeded | failed`
   - `advise`: `not-needed | skipped | succeeded | failed`
   - `new_ids: set[str]`
   - `failures` には短い種別と安全なエラー要約だけを持たせ、プロンプト・提案本文・活動タイトルを残さない。
   - catch-upに起因する `generate` / `advise` の個別runlog `error` にも同じ安全な種別・要約だけを保存する。例外の生本文、提案本文、活動タイトル、プロンプトを個別ログ側へ迂回して残さない。
2. 夜の `run` は `CatchUpResult.new_ids` を従来の即時判定除外へ渡し、H7の契約を壊さない。
3. `morning` に `--skip-catch-up` を追加する。
   - 既定は従来どおり追いつきON。
   - 指定時はAW、LLM、昨日ノート、昨日statsの生成・更新を行わず、既存Memoryから今日の表示と通知だけを行う。
4. 追いつきに1件でも失敗があった場合:
   - 朝処理は続け、終了コード0を維持する。
   - stdoutと通知へ `⚠ 昨日の追いつきは未完了（generate）` 等、失敗ステップ名だけを出す。
   - `morning` runlogに `partial: true` と安全な `note` を記録する。
   - `render_status` は直近partialを✅ではなく⚠で表示し、`doctor` は警告にする。`ok=True`だけで部分成功を上書きしない。
5. `_sync_checkbox_statuses` は、統合後のentriesと更新件数を返す。
6. `today` に `--no-sync` を追加する。
   - 既定は既存互換として同期ON。
   - 同期で変更したときは `↻ ノートのチェック状態をMemoryへ同期しました: N件` を一覧前に表示する。
   - `--no-sync` はノート走査とMemory書き込みを行わず、`ℹ 同期せずに表示しています` を表示する。
7. argparseのhelp、README、USAGEを次の意味に合わせる。
   - `morning`: 「追いつき（AW/LLM・書き込みを含む場合あり）→再描画→通知」
   - `today`: 「未完了一覧（既定でノートのチェックをMemoryへ同期）」

### テスト

- catch-up不要／generate成功／advise成功／各失敗の `CatchUpResult`。
- `run` のretro-advise直後判定除外が維持される。
- `morning --skip-catch-up` で `missing_days`、`cmd_generate`、`cmd_advise` が呼ばれない。
- 追いつき失敗でも朝一覧・通知は実行され、exit 0、runlogは `partial: true`、statusは⚠。
- partialの `note` とcatch-up由来の個別runlog `error` のどちらにも、アクション本文・活動タイトル・提案本文・プロンプトが入らない。
- `today` 同期0件／1件以上の表示。
- `today --no-sync` で `DailyNoteStore.read` と `append_entries` が呼ばれない。
- 既存の `today → done → today`、doneの冪等性、通知プライバシーのテストを維持する。

## §X4 [P1] 今日の候補と古い未完了を同時に見失わない

対象:

- `src/kaizenlog/memory.py`
- `src/kaizenlog/cli.py`
- `README.md`
- `docs/USAGE.md`
- `tests/test_round11.py`
- `tests/test_round12.py`
- 新規 `tests/test_ux_round13.py`

### 問題

現行UIは直近7日窓の未完了を全件同列に表示する。件数が増えると今日やるものを選びにくく、8日を超えるとMemoryに残っているのに一覧から無言で消える。

### 必須修正

1. 表示用の群分けヘルパー自体はMemoryを変更せず、未完了を次の3群へ分ける。`kaizenlog today` の既定チェック同期は§X3どおり維持し、表示だけを検証するテストは `--no-sync` を使う。
   - `recent`: `target_day - 7日` 〜 `target_day`（0〜7日前、現行todayと同じ8暦日）。新しい提案から並べる。
   - `stale`: `target_day - 30日` 〜 `target_day - 8日`（8〜30日前）。
   - `older`: `target_day - 31日` 以前（31日以上前）。
2. `kaizenlog today` の既定表示:
   - `recent` の先頭最大3件を `今日の候補` として表示する。
   - recent残件、stale件数、older件数を別々に表示する。
   - 例:

     ```text
     今日の候補 3件
     ...
     ほか直近7日の未完了 4件 / 8〜30日前 2件 / 31日以上 1件
     全件表示: `kaizenlog today --all`
     ```
3. `today --all` を追加し、全proposedを `直近7日` / `8〜30日前` / `31日以上` の見出しで表示する。表示だけでstatusをdone/supersededへ変更しない。
4. Obsidianの「📌 今日のアクション」は前日までの直近7日という既存対象を維持しつつ、チェックボックスは最大3件に絞る。
   - 対象範囲は `target_day - 7日` 〜 `target_day - 1日` の7暦日であり、todayのrecent範囲とは意図的に異なる。
   - 残り件数と古い未完了件数を表示し、`kaizenlog today --all` を案内する。
   - 最大3件は新しい提案から選ぶ。これは「優先度の推定」ではなく、現在の文脈へ近い候補を表示する決定論ルールであるとコメントする。
5. アクション0件の場合:
   - recentが0でもstale/olderがあれば「今日の候補なし。保留N件」を表示し、全件導線を出す。
   - 全期間0なら従来の「未完了のアクションはありません」を維持する。
6. morning通知は本文を出さない既存プライバシー原則を守り、`今日の候補 n件 / 保留 m件` の件数だけを出す。
7. KZN ID、チェック保持、消化率/PASS率、当日提案をtodayに含めるR1、done_date非破壊R2を維持する。

### テスト

- recent 5件で既定表示3件＋残件2件、`--all` で5件すべて。
- `target_day - 8日`、`target_day - 30日`、`target_day - 31日` の境界。
- recent 0・staleありで保留導線が出る。
- Obsidianセクションは最大3チェックボックス、残件数を表示し、既存 `[x]` を保持する。
- `--all` と既定表示でMemoryファイルが変わらない（§X3の既定同期を無効化した関数単体または `--no-sync --all` で検証）。
- `compute_action_stats` の14日集計窓は変更しない。

## §X5 [P1] Activity Logを「データが無い・省略された・表が壊れた」と誤解させない

対象:

- `src/kaizenlog/report.py`
- 必要なら `README.md` の出力例
- `tests/test_report_vault.py`
- 新規 `tests/test_ux_round13.py`

### 問題

- 0分時は「記録された活動はありませんでした」だけで、次に確認すべきことが分からない。
- 60行超のタイムラインは長時間上位60件へ置換されるが、省略件数・選別規則が表示されない。
- サイト・アプリ・タイトルは一部エスケープされる一方、カテゴリ名とAIツール名はそのまま表セルへ入る。カスタム値に `|` や改行があるとMarkdown表と読み上げ順を壊し得る。

### 必須修正

1. 0分の空状態を次へ変更する。

   ```markdown
   ActivityWatchから対象日のアクティブ時間を0分取得しました。
   PCを使わなかった場合は正常です。使用した場合は `kaizenlog doctor` でwatcherと対象日を確認してください。
   ```

   - 「収集成功」「watcher停止」のどちらかをコードが確認していない場合、断定しない。
   - 既存ノートのマーカー外は変更しない。
2. タイムラインは選別規則を常に短く表示する。
   - 例: `3分以上の画面ブロックを時刻順に表示。`
3. `max_timeline_rows` を超えた場合、元の対象件数と表示件数を表示する。
   - `total_blocks`（全ブロック）、`eligible_blocks`（`min_block_minutes`以上）、`shown_blocks`、`overflow_omitted` を別々に数える。
   - 例: `全106件中、3分以上は84件です。長時間の上位60件を時刻順に表示し、対象内の24件を省略しています。`
   - 件数は実配列から決定論的に算出し、LLMに作らせない。
4. `_markdown_table_cell(value: object) -> str` を共通化する。
   - `str(value)` を一行化する。
