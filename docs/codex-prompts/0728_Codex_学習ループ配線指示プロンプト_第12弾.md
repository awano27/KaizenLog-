# Codex 実装指示: 学習ループの配線 — 計測衛生とフィードバック還流 6件（J1〜J6）— 第12弾

対象リポジトリ: `C:\develop\KaizenLog\KaizenLog-`（Python / pytest）

**前提: 第11弾＋eval サンプル補完適用済みの HEAD（5b927c7 以降）。** ワーキングツリーの進行中変更は取り消さず、その上に積むこと。

## 背景

判定データ（verdict / 実測値）を集める仕組みは完成したが、**昨日の判定が LLM に渡っておらず、コーチは結果を知らずに毎晩提案している**（測るループはあるが学ぶループが未配線）。また、未実行アクションにも PASS/FAIL が付くため PASS 率が「行動効果とノイズの混合」になっており、拒否（合わない提案）と放置（未着手）の区別も取れない。本弾はこの学習信号を浄化して還流する。

実装順は §J1 → §J2 → §J3 → §J4 → §J5 → §J6 を推奨（J3/J4 が J1/J2 の集計定義に依存）。

## §J1 実行×判定の層別 — 「実行済みPASS率」を主指標にする

`src/kaizenlog/memory.py`（compute_action_stats 等）、`cli.py`（status・朝トースト）、`verdict.py` は変更しない（判定自体は全件続ける。層別は**集計・表示・プロンプト側**で行う）

1. `ActionStats` を拡張: `done_judged` / `done_passed`（done かつ判定あり）と `undone_judged` / `undone_passed`（未実行のまま判定あり）を追加
2. 表示の主指標を**実行済みPASS率**（done_passed / done_judged）に変更する: status の Kaizen実績行、📌 の統計行、朝トーストの「昨日の判定」。未実行判定が1件以上ある場合は「（未実行での達成 n件）」を併記
3. `summarize_for_prompt` に信号行を追加: 未実行PASS が期間内に2件以上あれば「行動せずに達成された条件が n 件ある。目標が緩いか、指標が行動と無関係の可能性を検討する」
4. 既存の pass_rate を参照している箇所（適応投与・較正等）は実行済みPASS率ベースに統一（定数名・コメントも更新）

テスト: 層別集計の各分岐 / done と undone が混在するケースの主指標 / 信号行の出現条件。

## §J2 skip シグナル — 拒否と放置を区別する

`src/kaizenlog/memory.py`、`cli.py`、`skills/daily-kaizen/SKILL.md`、`prompts/daily_advisor.md`

1. `MemoryEntry.status` に `skipped` を追加し、`skip_reason: str | None` フィールドを追加（旧 JSONL 互換: 欠落は None）
2. 検出2経路:
   - ノート記法: `- [-] KZN-...`（Obsidian の cancelled チェックボックス）を `update_statuses_from_note` で検出して skipped 化。行内に `｜理由: <text>` があれば skip_reason に保存
   - CLI: 既存の action 系サブコマンド群（`kaizenlog action ...`）に `skip <KZN-ID> [--reason TEXT]` を追加（action 群が無ければ `kaizenlog skip` として追加）
3. skipped の扱いを全経路で統一:
   - 消化率の**分母から除外**（拒否を「未消化」として dosing に誤カウントさせない）。表示は「提案N件 / 消化x% / スキップk件」
   - 📌 持ち越しから除外
   - `judge_entries` の対象外（現行の proposed/done フィルタで自然に除外されることをテストで固定）
4. `summarize_for_prompt` に「## スキップされた提案（同種を繰り返さない）」ブロック: 直近30日の skipped を理由付きで最大5件
5. `daily_advisor.md` に1行: 「スキップされた提案と同種のアプローチを繰り返さない。理由があればそれを尊重した代替を出す」
6. daily-kaizen SKILL.md に `- [-]` 記法の説明を追記

テスト: `- [-]` 検出と理由抽出 / 分母除外と表示 / 持ち越し除外 / プロンプトブロック / 旧 JSONL 互換。

## §J3 判定還流＋シェイピング規則 — コーチに昨日の結果を教える

`src/kaizenlog/memory.py`（summarize_for_prompt）、`prompts/daily_advisor.md`、`privacy_safe.md`

1. `summarize_for_prompt` に「## 直近の判定（最大3日・新しい順）」ブロックを追加。各行:
   `- KZN-... [✅PASS|❌FAIL] 実行済み|未実行|スキップ ｜ <行動先頭60字> ｜ PASS条件: <条件> ｜ 実測: <値>`
   （§J1 の層別ラベルを必ず付ける。判定エントリが無い日はブロック自体を省略）
2. `daily_advisor.md` にシェイピング3規則を追記:
   - (a) **実行済みFAIL** は「本人は動いたが目標が届かなかった」ケース。同じ行動をより小さい一歩に分割して「（継続）」として再提案してよい（既存の「未完了を再提案しない」規則の**明示的な例外**であることを両方の箇所に書く）
   - (b) 同一の行動・指標が2〜3連続PASSなら、維持を承認した上で `kaizenlog experiment new ...` の昇格例を添付する（現在の「新しい提案の場合だけ実験例を添える」制限を撤廃し、この文言を書き換える）
   - (c) 「計画と実績」の冒頭1文で、昨日のPASSを具体的に承認する。FAILは本人を責めず、ログから推定できる障害を1つだけ挙げる
3. 上方分岐: `summarize_for_prompt` に、実行済みPASS率≥60% かつ消化率≥70%（直近14日、`_THRIVING_*` 定数）のとき「現状の負荷は適正。維持を明確に承認し、1件だけ一段挑戦的な提案をしてよい」の指示行を追加（_DOSING の対）
4. privacy_safe.md にも (a)(c) 相当を反映（トーン規則は共通、実験昇格例は privacy_safe の既存方針に従う）

テスト: 判定ブロックの整形（3日窓・層別ラベル・省略条件）/ _THRIVING 分岐の境界。

## §J4 適応投与の決定論化 — 投与量を機械で保証する

`src/kaizenlog/advice_evidence.py`、`cli.py`（evidence 構築の配線）、`memory.py`

1. evidence 構築経路に `ActionStats`（§J1/J2 適用後の消化率）を渡し、`max_actions` を決定論で設定:
   `proposed >= 6 かつ done_rate < 0.4 → 1` / `0.4〜0.6 → 2` / それ以外 → 3
   既存の max_actions 決定ロジック（short_record 等）とは **min() で合成**する（両方の制約を満たす）
2. `normalize_advice_cardinality` と validate の既存 max_actions 強制配管をそのまま使う（追加実装最小）
3. プロンプト側のソフト指示（第2弾 A3-3）は「なぜ1件なのか」の理由説明として残し、文言を「システムが件数を制限している」前提に更新

テスト: 消化率帯ごとの max_actions / 既存ロジックとの min 合成 / 3件返した LLM 出力が1件に正規化されるエンドツーエンド。

## §J5 ❌の距離フレーミング — 二値失敗を「残距離」に変える

`src/kaizenlog/verdict.py`（format_verdict_suffix）

1. 機械構文judged の suffix を変更:
   - FAIL: `｜判定: ❌ 実測45（目標40・あと5）`。目標との差が**10%以内**なら `❌ あと一歩（実測45/目標40）`
   - PASS: `｜判定: ✅ 実測35（目標40）`
   - 「あと」の方向は target_op から決める（`<=` なら超過分、`>=` なら不足分）。数値は `{:g}`
2. 既存の冪等置換（`｜判定:` プレフィックスで検出・置換）と互換であること。📌 持ち越し表示・朝トースト（件数のみ）は既存方針のまま
3. 旧 suffix（「❌（実測 52）」形式）が残るノートの再判定時も正しく置換されること

テスト: 各分岐（<= / >= 両方向、10%境界）/ 冪等置換 / 旧形式置換互換。
