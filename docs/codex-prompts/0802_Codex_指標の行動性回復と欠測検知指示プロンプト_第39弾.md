## Phase 1 — §A: PASS指標の行動性回復(T4-1)

**本弾の中核。§A を完了せずに Phase 2 以降へ進まないこと。**

### §A1 レート指標を既定にするプロンプト契約 `[S / 最優先]`

- **現状**: `prompts/daily_advisor.md` の `pass` 規則が `(例: context_switches <= 40)` という生カウント例だけを提示し、`render_pass_metric_contract` は「当日使用可能 / 当日使用禁止」の2分類しか出さない。LLMは可能な指標の先頭にある生カウントを選び続ける
- **修正方針**:
  - `daily_advisor.md` の `pass` 規則の例を **レート指標**に差し替える(`context_switches_per_hour <= 65` 等)。既存の「機械構文必須」「自由文PASS禁止」「当日使用可能なPASS指標だけを使う」は文言も含めて変えない
  - 同じ箇所に1行追加する: **「同じ行動を測れる指標が複数あるときはレート指標(`*_per_hour` / `*_per_session`)を選ぶ。生カウントは、稼働量が変わっても意味が保たれる場合だけ使う」**
  - `render_pass_metric_contract` の出力を **3見出し**に変える:
    - `## 当日使用可能なPASS指標(推奨・レート)` — available のうち `_per_hour` / `_per_session` で終わるもの
    - `## 当日使用可能なPASS指標(条件付き・生カウント)` — available の残り
    - `## 当日使用禁止のPASS指標` — 現行のまま
  - 分類は**接尾辞の判定**で行い、指標名のハードコード列を新設しない(将来のレート指標追加で自動的に推奨側へ入る)
- **注意**: `_PASS_METRIC_CONTRACT_MARKER` の出現数チェック(`system_prompt.count(...) != 1`)は現行のまま維持する。契約テキストの見出し追加はマーカー差し込みの後段であり、マーカー自体を増やさない
- **受け入れ条件**:
  - 推奨側が空(レート指標が1つも使えない日)でも見出しが壊れず、`なし` と出ること
  - 条件付き側が空でも同様
  - `available_pass_metrics` の返り値そのものは変更しないこと(可否の判定ロジックに手を入れない)
  - `daily_advisor.md` に生カウントの例が残っていないこと(`context_switches <= 40` の文字列が消えていること)

### §A2 生カウントPASSの入口ガード `[M / high]`

- **現状**: `advisor.py` の `evidence_gated_action_errors` は、当日 evidence で測れない指標を弾くが、**測れるが分母が薄い日の生カウント**は通す。8/1(稼働13.9分)で `ai_tool_errors <= 40` が保存され、翌日 `406` で `fail` になった
- **修正方針**: `evidence_gated_action_errors` に判定を1つ足す。生カウント指標(レート接尾辞を持たず、かつ `category_minutes:` / `site_minutes:` でないもの)を PASS に使っていて、**当日の `total_minutes` が下限(既定60分)未満**なら violation を返す
  - violation 文言は代替を明示する: `最小アクション{index}: 本日の記録は{X}分のため生カウント指標「{metric}」は翌日の稼働量に左右されます。レート指標({候補})を使うこと`
  - 候補の提示は `available_pass_metrics` の推奨側から選ぶ。推奨側が空なら候補を書かず理由だけを返す
  - 下限は定数化する(`_RAW_COUNT_MIN_ACTIVE_MINUTES = 60.0`)。`metric_from_stats` の `context_switches_per_hour` が使う 60分下限と同じ値であることをコメントで示す
- **注意**: 禁止事項(d)のとおり、この violation は**修復プロンプト経由で作り直させる**ためのものであり、修復後も違反する場合の最終挙動は現行の contract 違反処理と同じにする。提案ゼロを新たに許容する分岐を作らない
- **受け入れ条件**:
  - `total_minutes=13.9` の evidence で `pass: ai_tool_errors <= 40` → violation が返り、文言に代替指標名が含まれる
  - 同じ evidence で `pass: ai_tool_errors_per_session <= 2.0` → violation なし
  - `total_minutes=180` の evidence で `pass: ai_tool_errors <= 40` → violation なし(稼働十分なら生カウントは許可)
  - `pass: category_minutes:執筆・ノート >= 8` は稼働量に関わらず violation なし(カテゴリ分は生カウントだが行動そのものの量である)
  - 推奨側が空の evidence でも例外を出さず violation 文言が組み立つこと

### §A3 判定側の計測カバレッジゲート `[M / high]`

- **現状**: `verdict.py` の `judge_entries` / `backfill_verdicts` は、対象日の stats から `metric_from_stats` で値が取れれば必ず `pass` / `fail` を確定する。レート指標は分母下限で `None` を返すため守られているが、**生カウントは無防備**
- **修正方針**: 生カウント指標の判定時に、対象日の `total_minutes` が **直近7日(対象日を含まない)の中央値の50%未満**なら判定を確定させず、判定不成立として扱う
  - 判定不成立は**新しい verdict 値を作らない**。現行の「判定できない」経路(値が `None` のときと同じ扱い)に合流させる
  - 履歴が3日未満のときはゲートを適用しない(中央値が信用できないため fail-closed で従来どおり)
  - 表示側には理由を出す: `（7/31提案・判定 — 計測が薄い日のため判定不成立）`。既存の `format_verdict_suffix` / `format_action_verdict_tag` の文言体系に合わせ、**達成・未達を断定しない**
- **注意**: 制約(a)のとおり、**過去に確定済みのエントリを再判定しない**。ゲートは新規判定時のみ。`backfill_verdicts` 経路でも、既に `verdict` を持つエントリには適用しない
- **受け入れ条件**:
  - 8/1相当(対象日 `total_minutes=13.9`・直近7日中央値100分)で生カウント `ai_tool_errors` の判定不成立、`verdict` が書かれないこと
  - 8/2相当(`total_minutes=172.8`・中央値100分)では従来どおり判定されること
  - 履歴2日しかない場合はゲートが効かず従来どおり判定されること
  - レート指標は本ゲートの対象外(既に分母下限を持つため二重ゲートにしない)こと
  - judge 経路と backfill 経路の**両方**にテストを置くこと(片側検証にしない)

## Phase 3 — §C: digest の意思決定化(T4-3)

### §C1 成果行と目標行の追加 `[S / medium]`

- **現状**: 第38弾の `digest.py` `build_digest` は 稼働 / AI作業 / 摩擦ワースト / 提案件数 / 詳細リンク の5行。**その日に何が前へ進んだか**が無い。`outcome_git` の集計と `goal` マーカーの目標文はどちらも既に存在するのに digest へ配線されていない
- **修正方針**: `build_digest` に2行を**この順序で**足す(稼働行の直後、摩擦ワーストの前):
  - `- 目標: {goal_text}`(goal が無い日は行ごと省略)
  - `- 成果: {repo} {N}コミット {+X/-Y}行`(`outcome_git` の結果が無い/取得失敗なら行ごと省略)
- **注意**: `build_digest` は決定論のみ・LLM文禁止・評価語の自己検査(`良い` / `悪い` / `改善`)を通る。**目標文はユーザーの自由記述であり評価語を含みうる** — 現行の自己検査は該当時に `None` を返して digest 全体を落とす実装なので、**目標行だけは自己検査の対象から除外**するか、目標行を落として他を残す分岐にする。どちらを選んだか報告に書くこと
- **受け入れ条件**:
  - goal 有り / 無し、outcome 有り / 無しの4通りで行の有無が正しいこと
  - 目標文に `改善` が含まれる日でも digest 全体が `None` にならないこと
  - 順序が `稼働 → AI作業 → 目標 → 成果 → 摩擦ワースト → 提案件数 → 詳細` で固定されること

### §C2 「今日の1手」行 `[S / medium]`

- **現状**: digest の `- 今日の提案: {n}件 / 未完了: {m}件` は件数だけで、**何をやればいいか**が無い
- **修正方針**: 未完了エントリのうち**最新1件**の trigger 相当(行動文の先頭40字)を1行で出す: `- 今日の1手: {KZN-ID} {行動文の先頭40字}…`
  - 未完了0件なら行ごと省略。redactor を通すこと
  - 第38弾の `TERMINAL_STATUSES` を除外に使い、`proposed` のみを対象にする
- **受け入れ条件**: 未完了0件で行が出ないこと / `retired` のエントリが選ばれないこと / 40字超で末尾が `…` になること

- **修正方針**:

  - 「☑ 指標は達成済み」ブロックは**個別行を出さず件数1行**に畳む: `☑ 指標は達成済み {n}件（習慣化するなら kaizenlog today --all）`

- **注意**: 第38弾 §A の寿命管理(`unmeasurable` / `graduated` / `retired`)による除外はそのまま効かせる。本弾は**除外ではなく表示の圧縮**であり、件数から消してはならない
- **受け入れ条件**:
  - 未完了5件 → 個別行1件 + `ほか直近7日の未完了 4件`
  - 未完了0件 → 未完了ブロックが出ないこと
  - 達成済み3件 → 個別行0・件数1行
