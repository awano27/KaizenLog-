# Codex 実装指示: 計測・判定の信頼性5件(偽PASS・判定漏れ・集計汚染の前提工事)— 第10弾

対象リポジトリ: `C:\develop\KaizenLog\KaizenLog-`(Python / pytest)

**前提: 第1〜9弾適用済みのワーキングツリー。** 実装順は §M5 → §M3 → §M1 → §M4 → §M2 を推奨(M1〜M5 は相互独立だが、M2 が最も広く cli.py に触るため最後)。

## 背景

北極星指標(消化率/PASS率)とLLMへの適応還流は実装済みだが、**その数字を汚染する構造的な穴が5つ**ある: (1) 実在しないカテゴリ名のPASS条件が恒久的に偽PASSする、(2) 判定は提案翌日の1回きりで、PC未起動日の提案が永久未判定のままPASS率の分母から静かに消える、(3) Codexアダプタの集計に上書き消失・日跨ぎ過大計上・二重加算がある、(4) AFK watcher不在日は終日アクティブ計上なのに欠測フラグが残らず下流が正常値として扱う、(5) 失敗トースト通知自体が失敗しても無音。汚染された数字はプロンプトに自動還流されるため(適応投与)、人間が気づく機会がない。**機能追加より先にこの前提工事を行う。**

設計原則(従来どおり厳守): 数字と判定はコードが決定論的に行い、LLMは解釈のみ / マーカー区間の外は変更しない / 夜間・朝の無人実行を止めない(失敗は縮退して続行し、実行ログに残す)/ 冪等性(再実行で結果が変わらない)を守る。

## §M1 [High] PASS指標の実在検証(偽PASS入口ガード)

`src/kaizenlog/advice_format.py`、`src/kaizenlog/experiments.py`、必要に応じ `src/kaizenlog/advice_evidence.py`

**問題**: `compute_metric` は `category_minutes:<名前>` の未知カテゴリを 0.0 で返す(experiments.py の category_minutes 分岐、152行付近)。LLM が実在しないカテゴリ名(例: ユーザー定義に無い「SNS」)で `PASS: category_minutes:SNS <= 30` を書くと、0.0 <= 30 で**恒久的に偽PASS**する。`is_known_metric` は任意サフィックスを許容するため防げない。

1. **入口ガード(主対策)**: 提案受入時の検証(`_validate_advice_raise` / JSON層の検証)に以下を追加:
   - PASS条件の指標が `category_minutes:<名前>` の場合、`<名前>` が**設定のカテゴリ定義**(DEFAULT_RULES + ユーザールールのカテゴリ名集合)に実在しなければ契約違反(修復ループ対象)。既知カテゴリ名集合は evidence 構築時に渡す(advisor → validate の既存のデータ受け渡し経路に乗せる。検証層から config を直接読まない)
   - `site_minutes:<ドメイン>` の場合、当日 stats に観測されたドメイン集合に無ければ契約違反(提案は観測事実に根拠を持つ原則のため。**ブロック成功で0分になった既知ドメインの後日判定は §M2 の判定側の話であり、入口では「提案日当日に観測されていること」を要求してよい**。この理由をコメントに明記)
   - **PASS条件の指標が当日の環境で計測不能な場合も契約違反とする**: `focus_blocks`(入力watcher未導入)、`site_minutes:*`(ブラウザwatcher未導入)、`ai_*`(aiwork無効)。計測可否は evidence が既に保持する測定限界情報(watcher有無)から導出する。**実例(2026-07-26 の実運用データで確認)**: 入力watcher未導入の環境で `PASS: focus_blocks >= 1` の提案が保存され、compute_metric が None を返し続けて永久未判定(§M2 の無言スキップ)になった。入口で弾けば修復ループが計測可能な指標に書き直させられる
2. **防御側(副対策)**: `compute_metric` / `metric_from_stats` で `category_minutes:<名前>` の `<名前>` が既知カテゴリ名集合に無い場合は **0.0 ではなく None(未計測)** を返す。既知カテゴリで当日 stats に無いだけなら従来どおり 0.0(その日0分は正当)。`site_minutes:` は従来どおり欠損=0.0 を維持(サイトブロック成功時の0分判定が正当なため。この非対称の理由をコメントに明記)。既知カテゴリ名集合は引数で受け取り、呼び出し元(cli.py の generate / verdict 経路)が config から渡す。**引数省略時(後方互換)は従来挙動**

テスト: 未知カテゴリのPASS条件が契約違反になり修復ループへ回る / 既知カテゴリ0分は 0.0 のまま / 未知カテゴリの compute_metric が None を返し verdict が無言スキップでなく §M2 のログに載る / site_minutes 欠損は 0.0 維持 / 入力watcher無し環境で focus_blocks のPASS条件が契約違反になる / 引数省略時のデグレなし。

## §M2 [High] 遅延PASS判定バックフィル(done日基準・7日窓)

`src/kaizenlog/cli.py`(cmd_generate)、`src/kaizenlog/verdict.py`、`src/kaizenlog/memory.py`、`src/kaizenlog/experiments.py`

**問題**: 機械判定は `proposal_day = 実行日-1` の1回しか走らない(cli.py の judge_entries 呼び出し箇所)。翌日にPC未起動・watcher停止だった提案は `compute_metric` が None → 無言スキップ(verdict.py 135行付近)で**永久未判定**となり、PASS率の分母から静かに消える。消化率が7日窓なのに判定窓が1日という非対称。

1. `cmd_generate` の既存判定の後に**バックフィル判定**を追加: `load_entries` から「verdict 未設定かつ提案日が過去7日以内」のエントリを走査し、後追い判定する
2. **判定基準日の意味論**(コメントに明記): 測定日は `done_date + 1日`(行動の効果を測る)。`done_date` が無い(未実行)エントリは `提案日 + 1日`(提案の妥当性を測る)。エントリに `done_date` フィールドが無い既存データは欠損許容(提案日基準にフォールバック)
3. 実測値は当日再計算ではなく**保存済み stats からの復元**(`metric_from_stats`)を使う。測定日の stats ファイルが無い場合はスキップ(次回の generate で再試行される)。`ai_avg_turns` 等 `metric_from_stats` 非対応の指標もスキップ(既知の制約としてコメントに明記)
4. 冪等性: 既存の「同一 verdict は空差分」(verdict.py の同一判定スキップ)と追記型後勝ち JSONL に乗せる。バックフィルで判定が付いたら、**提案日ノートの ADVICE 区間への注記書き戻し**(既存の annotate 処理)も同様に冪等に行う
5. **無言スキップの可視化**: 判定をスキップした件数(stats欠損 / 指標非対応 / compute_metric=None)を generate のコンソール出力と runlog に1行で記録する(例: `verdict backfill: judged 2, skipped 3 (no-stats 2, unsupported 1)`)

テスト: 翌日に stats が無かった提案が翌々日の generate で判定される / done_date ありは done_date+1 の stats で判定される / 同一エントリへの再実行で JSONL が増殖しない / 注記の二重付与が起きない / スキップ件数のログ内容。

## §M3 [High] Codexアダプタの集計修正3点

`src/kaizenlog/aiwork_codex.py`

**問題**: (a) 同一 `session_id` が複数の rollout ファイルに分かれる(resume)と `sessions[session_id]` を丸ごと上書きし、先に読んだファイルの往復数・ツール数・エラー数が消える(Claude 側 aiwork.py はsid単位でマージ蓄積しており非対称)。(b) `output_tokens` は累積値の最大を採用するため、深夜跨ぎセッションで前日分が当日に過大計上される。(c) `api_calls` が `event_msg/agent_message` と `response_item/message(role=assistant)` の**両方**で加算され、両形式併存ログで二重計上。

1. **(a) sid単位マージ**: Claude 側アダプタと同じ方式で、既存 sid があればカウンタ類(user_turns / tool_calls / tool_errors / aborts 等)を加算マージ、時刻は min(開始)/max(終了) を採用する
2. **(b) 日跨ぎトークンの差分計上**: セッションごとに「対象日ウィンドウ開始より前の最後の累積値」を base とし、`ウィンドウ内の最大累積値 − base` を当日分とする(base が無ければ最大値をそのまま)。前日ディレクトリも走査対象である既存仕様を利用して base を得る
3. **(c) api_calls の系統統一**: セッション内に `response_item/message` 形式が1件でも存在する場合はそちらのみで数え、無い場合に限り `event_msg/agent_message` で数える(形式の混在ログで二重計上しない。この優先順の理由をコメントに明記)

テスト: 合成 JSONL 2ファイルに分割した同一セッションで往復数・ツール数が合算される / 前日から累積が続くセッションで当日分だけが計上される / 両形式併存ログで api_calls が二重にならない / 単一形式ログの従来挙動維持。

## §M4 [Medium] AFK欠測フラグの保存と測定限界通告

`src/kaizenlog/collector.py`、`src/kaizenlog/stats.py`、`src/kaizenlog/advice_evidence.py`

**問題**: AFK watcher 不在時は終日をアクティブ区間として採用する(collector.py 292行付近、doctor は警告のみ)。その日の stats に欠測の痕跡が残らないため、下流(advice_evidence / 実験計測 / 前日比較)は過大な合計時間を正常値として扱う。

1. collector が「AFK bucket を利用できたか」を収集結果に含めて返し、stats JSON に `afk_watcher_available: bool` として保存する(既存の stats スキーマに1キー追加。読み手が居ない旧 stats は欠損=true 扱いで後方互換)
2. `advice_evidence` で `afk_watcher_available == false` の日は、既存の測定限界 L1〜L11 の様式に従い新しい L 項目を追加: 「AFK未計測のため合計時間・カテゴリ時間は過大の可能性(離席時間を含む)」。あわせて合計時間系の確定事実の扱いを既存の降格/注記パターン(activity_sha256 mismatch 時の降格と同様式)に合わせる
3. 判定・実験計測の挙動自体は本弾では変更しない(注記のみ。判定から除外するかは将来判断。スコープ外である旨をコメントに明記)

テスト: AFK bucket 無しの収集で stats にフラグが保存される / フラグ false の日に L 項目が evidence に現れる / 旧 stats(キー欠損)で従来挙動。

## §M5 [Medium] 失敗通知の故障検知(静かな故障の最後の砦)

`src/kaizenlog/notify.py`、呼び出し元(`src/kaizenlog/cli.py` の失敗ハンドラ・morning)

**問題**: `notify()` は PowerShell の returncode を検査せず capture_output で握り潰す(notify.py 49行付近)。タスクスケジューラの非対話セッションではバルーン通知が表示されない可能性が高く、「失敗を知らせる仕組みが静かに失敗する」二重の静寂になっている。

1. `notify()` が subprocess の returncode / 例外を検査し、成否を `bool` で返す(例外は引き続き外へ漏らさない — 通知失敗で本処理を落とさない原則は維持)
2. 呼び出し元は戻り値 false のとき runlog に `notify_failed` を記録する。**記録処理自体も try で包み、二次例外で元の例外処理を壊さない**(この理由をコメントに明記)
3. `kaizenlog status` の表示に、直近の runlog に `notify_failed` があれば1行警告を追加(「⚠ 失敗通知の送出に失敗した記録があります。通知経路を doctor で確認してください」程度)

テスト: PowerShell 失敗を模擬(returncode≠0 / 例外)して False が返る / runlog に記録される / 記録失敗でも例外が漏れない / status の警告行。
