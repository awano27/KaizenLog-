## Phase 1a — §A: `kaizenlog handoff`(エージェント申し送り注入)

**目的**: 実測した協働実績を、任意リポジトリの CLAUDE.md / AGENTS.md 内のマーカー区間へ冪等再生成する。エージェントが毎セッション失っていた「前回の教訓」を標準コンテキスト化する。

### §A1 新モジュール `src/kaizenlog/handoff.py`

- マーカー名 `AGENT_CONTEXT_MARKER = "kaizenlog:agent-context"` を `src/kaizenlog/vault.py` のマーカー定数群(L25-29)に追加し、handoff.py から import する
- 書き込みは既存の **`vault.upsert_section(content, marker, section_md, position="bottom")`(vault.py L64)** を再利用する(任意テキストに対して動作する汎用関数。自前の置換ロジックを書かない)
- 対象ファイルにマーカーが無い場合は末尾に追記、ある場合は区間のみ置換。**区間外は1バイトも変えない**
- 生成セクションの先頭に固定ヘッダを入れる: 「このセクションは KaizenLog が実測データから自動生成(再実行で上書き)。手動メモはマーカーの外へ。生成日: YYYY-MM-DD」

### §A2 セクション内容(すべて決定論・直近30日)

以下の4ブロック。**データが無いブロックは「(計測なし)」と1行で明示**する:

1. **リトライ傾向**: `stats.load_stats`(stats.py L295)で30日分を読み、retry_chains 件数の合計・直近7日の傾向(増/減/横ばい)を1-2行
2. **頻出ツールエラー**: stats v2 の tool_errors 集計。多い日の件数と30日合計
3. **連続FAIL中のKZN施策**: `memory.py` の `_consecutive_metric_fails`(L528)相当の結果を使う。private のため **公開ラッパー `consecutive_fail_actions(...)` を memory.py に追加**し、handoff からはそれを呼ぶ。「N日連続FAIL: KZN-... (metric 条件)」形式
4. **skilled化待ちPRMクラスタ**: `promptledger.load_prompt_ledger`(promptledger.py L44)で status=new かつ count 上位3件。表示は `_redact_display`(L143)済みの代表文のみ

### §A3 CLI配線

- `cli.py` の subparsers(L1608)に `handoff` を追加: `kaizenlog handoff [--target <path> ...] [--dry-run]`
- `--target` 未指定時は config の `[handoff] targets = ["path/to/CLAUDE.md", ...]` を使う(`config.py` に `HandoffConfig` を追加。未設定なら「targets が未設定」とエラー表示して終了コード1)
- `--dry-run` は生成セクションを標準出力へ表示し、ファイルへ書かない
- 書き込みは `vault.atomic_write_text`(vault.py L13)を使う

### §A4 config

`kaizenlog.toml` にコメント付きサンプルを追記:

```toml
# [handoff]
# targets = ["C:/develop/myrepo/CLAUDE.md"]
```

### §A5 受け入れ条件

- `tests/test_round27_handoff.py` を新規作成:
  - 2回連続実行で出力ファイルが完全一致(冪等性)

  - マーカー無しファイルへの初回追記

## Phase 1b — §B: プロンプト資産ROIランキング

**目的**: PRM台帳の各クラスタに「スキル化したらどれだけ得か」の実数を与え、mark skilled 済みは削減実績を複利で見せる。

### §B1 ROI集計(新規 `src/kaizenlog/promptroi.py`)

- 入力: `load_prompt_ledger` のエントリ + `aiwork.scan_user_prompts`(aiwork.py L549)の直近30日プロンプト
- 各クラスタへの帰属判定は既存 `promptledger.find_matching_entry`(L124)/ `similarity_ratio`(L116)を再利用
- 算出(決定論): クラスタ別 **再発回数(30日)** と **推定関与トークン**(そのプロンプトが属するセッションの output tokens 合計。按分はしない。セッション単位でしか取れないことを表の脚注に明記)
- `PromptLedgerEntry`(L29)に `marked_on: str | None` フィールドを追加し、`mark_prompt_entry`(L280)で skilled/dismissed にした日付を記録(既存JSONL行に無い場合は None として読む後方互換必須)
- skilled 済みクラスタ: `marked_on` 前30日 vs 後30日の再発回数を比較し「削減 N回 / 約M tokens」を出す

### §B2 CLI

- `kaizenlog prompts --roi` を追加(pr_sub L1664 配下ではなく既存 `prompts` パーサーのフラグ。`--unhandled` L1669 と同居)
- 出力: ROI降順の表(PRM-ID / 再発30d / 推定tokens / status / skilled効果)

### §B3 週次連携

- `weekly_context.render_weekly_context`(weekly_context.py L103)に「プロンプト資産ROI」小節を追加: 上位3件+skilled削減実績1行。データ無しなら小節ごと省略

### §B4 受け入れ条件

- `tests/test_round27_prompt_roi.py`: 帰属判定・marked_on 後方互換(旧形式JSONL読込)・before/after削減計算・空台帳で表なし
- 確認: `./.venv/Scripts/python.exe -m kaizenlog.cli --config kaizenlog.toml prompts --roi`

## Phase 2 — §C: ループ税メーター

**目的**: retry連鎖で燃えたトークンを「エピソード」単位で会計し、金額つきで日誌と status に1行刻む。

### §C1 エピソード化(aiwork.py 拡張)

- 既存 `detect_retry_chains`(L503)の `RetryChain` をエピソードとみなす(新概念を作らない)
- 浪費トークンの定義(決定論・注記必須): チェーンに属する試行のうち**最終試行を除く**試行が属するセッションの output tokens をセッション単位で合算。プロンプト単位のトークンが取れない場合は「tokens不明」と表示(捏造禁止)
- 金額換算は既存 `resolve_output_price`(L79)/ `DEFAULT_OUTPUT_USD_PER_MTOK`(L65)を再利用

### §C2 既存バグ修正(必須)

`DEFAULT_OUTPUT_USD_PER_MTOK` は部分一致の順序評価のため、`gpt-4o-mini` が先行する `gpt-4o` にマッチして 10.0 USD と誤解決される。**`gpt-4o-mini` を `gpt-4o` より前に移動**し、回帰テストを追加。

### §C3 表示

- 日誌の AI作業セクション(`render_aiwork_markdown` L842)に1行追加: `💸 ループ税: $X.XX(Nエピソード / K tokens)`。config `[aiwork] usd_jpy = 150.0` が設定されていれば `¥N` 換算表示、未設定ならUSD
- `kaizenlog status` に同じ1行
- `render_weekly_context` に「今週最大のループ」: 日付・往復数(`RetryChain.length` L499)・浪費tokens・tool_error有無。`retry_chain_excerpts`(L742)の redact 済み抜粋1件

### §C4 閾値通知(小)

config `[aiwork] loop_tax_alert_usd`(未設定なら無効)。`run` / `generate` 実行時に当日ループ税が閾値超過なら `notify`(notify.py L13)でバルーン1回。

### §C5 受け入れ条件

## Phase 4 — §E: パーソナルMETR実験(`kaizenlog abtest`)

**目的**: 「AIで速くなったと思う(予測)/感じた(体感)/実際どうだったか(実測)」の3段ギャップを自分のデータで出す。

### §E1 実験タイプ追加

- `experiments.py` を拡張: 実験種別 `abtest`。`kaizenlog abtest new --predict <+N%> [--days 28]` で開始。予測値はフロントマター(`_set_frontmatter_field` L423 方式)に保存
- AI利用日の判定(決定論): stats v2 の当日 api_calls > 0(**internal_ai_sessions 除外後**。stats.py L50 参照)
- 実測: 対象期間の「開発カテゴリ分」を AI利用日群 / 非利用日群に分け、`weekday_baseline`(L322)で同曜日正規化した上で `effect_size`(L349)を算出

### §E2 終了と体感入力

- `kaizenlog abtest finish` → `--felt <+N%>` で体感値を入力させ、実測効果量と合わせて確定
- **非AI日サンプルが3日未満なら「実測不成立(サンプル不足: N日)」と表示し、効果量を出さない**(無い指標は無いと言う)

### §E3 SVGカード(決定論・依存追加なし)

- 新規 `src/kaizenlog/cardgen.py`: f-string でSVG文字列を組み立て `<memory_dir>/cards/abtest-<id>.svg` に保存。内容: 予測 / 体感 / 実測 の3バー+期間+サンプル数。数値以外の文言は固定文字列(LLM不使用)
- サンプル不足時は「不成立」デザイン(バー無し・理由表示)で必ず生成する

### §E4 日誌連携

- 実験終了日の日誌 Kaizen セクションに1行: 「📊 abtest完了: 予測+30% / 体感+20% / 実測−12%(カード: 相対パス)」。数値が不成立なら不成立の旨

### §E5 受け入れ条件

- `tests/test_round27_abtest.py`: AI日/非AI日の分割・internal除外・サンプル不足時の不成立挙動・SVGが well-formed XML であること(`xml.etree.ElementTree.fromstring` でパース可)・フロントマター往復
- 確認: `kaizenlog abtest new --predict +30 --days 28` → `abtest status`
