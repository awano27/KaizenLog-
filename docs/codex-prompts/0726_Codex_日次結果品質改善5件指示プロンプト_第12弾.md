## §Q1 [High] 修復専用プレースホルダーを利用者向け出力へ漏らさない

対象:

- `src/kaizenlog/advisor.py`
- `src/kaizenlog/advice_format.py`
- `tests/test_advice_evidence.py`
- 新規 `tests/test_round12.py`

### 問題

`_contract_repair_prompt` / `_sanitize_repair_source` は、元回答に含まれる観測数値やKZN IDを再利用させないため、`数値省略`・`既存アクション`等へ置換して修復モデルへ渡す。モデルがその語を自然文としてコピーすると、現状のJSON構造検証・意味検証を通過し、そのまま日誌と翌日アクションへ保存される。

実例:

```text
その状態で最初の数値省略分間、他のアプリを起動しない。
```

これは利用者が実行できず、修復機構の内部表現がUIへ漏れた状態である。

### 必須修正

1. 修復プロンプト内の置換語を、人間向けに見える日本語ではなく、明確な内部センチネルへ変更する。
   - 例: `__KZN_REPAIR_NUMBER__`、`__KZN_REPAIR_ACTION_ID__`
   - センチネル名は定数化し、生成・検証で同じ定義を使う。
2. JSONの利用者向け全文字列フィールドを検査し、修復センチネル、`数値省略`、`§FACT...§`等の既知内部トークンが残っていれば契約違反にする。
   - 対象: `plan_review`、`proposals`、`actions`、`ai_review` の表示文字列。
   - `fact_ids` の正規の `[F#]` は対象外。
3. 初回回答と修復回答の両方に同じ検証を適用する。
4. `render_advice_markdown` / `render_reader_advice` にも防御的な最終チェックを置く。
   - JSON検証を通過した内部トークンがあれば `AdviceContractError`。
   - 自動的に曖昧な日本語へ置換して保存してはならない。
5. 内部トークン違反は「renderer bug」ではなく、モデル出力の契約違反として扱う。

### 非目標

- 数字をすべて禁止しない。
- `[REDACTED]` を一律禁止しない。これはプライバシー設定の正当な表示になり得る。
- プレースホルダーを空文字へ置換して無理に保存しない。

### テスト

- `数値省略` を含むactionが拒否される。
- 内部センチネルを含むproposal/action/ai_review/plan_reviewがすべて拒否される。
- 通常の数値を含むPASS/FAILは従来どおり通る。
- 修復回答にセンチネルが残った場合、日誌へ保存されず既存の縮退経路へ入る。
- マーカー区間外のテキストは不変。

## §Q2 [High] ActivityWatchとAIテレメトリの観測期間を分けて表示する

対象:

- `src/kaizenlog/collector.py`
- `src/kaizenlog/aiwork.py`
- `src/kaizenlog/aiwork_codex.py`
- `src/kaizenlog/stats.py`
- `src/kaizenlog/advice_evidence.py`
- Activity Logレンダリング箇所
- `tests/test_collector.py`
- `tests/test_aiwork.py`
- `tests/test_aiwork_adapters.py`
- 新規 `tests/test_round12.py`

### 問題

ActivityWatchイベントとClaude Code / Codex JSONLは別のデータ源で、収集開始時刻・最終観測時刻が異なる。現状は同じ「当日の結果」として並ぶが、各値が一日のどの時間帯を覆うかが分からない。

この状態では、ActivityWatchの `AI作業 44m` とAIテレメトリの `出力トークン 316,388` を同じ観測窓の値だと誤解しやすい。

### 必須修正

1. stats JSONへデータ源別観測窓を保存する。

```json
{
  "source_windows": {
    "activitywatch": {
      "first_observed_at": "ISO-8601|null",
      "last_observed_at": "ISO-8601|null",
      "observed_span_minutes": 0.0
    },
    "ai_telemetry": {
      "first_observed_at": "ISO-8601|null",
      "last_observed_at": "ISO-8601|null",
      "observed_span_minutes": 0.0
    }
  }
}
```

2. 観測窓は実イベント／実セッションの最小・最大時刻から決定論的に算出する。
   - データが無い場合は `null` と0分。
   - 日付境界で対象日にクリップする。
   - タイムゾーンは既存configの `timezone` を使う。
3. Activity Logの各該当セクションへ簡潔に表示する。
   - 例: `画面活動の観測範囲: 17:23–23:07`
   - 例: `AIテレメトリの観測範囲: 07:43–23:07`
4. 2つの観測開始時刻が60分以上ずれる場合、次の注意を表示する。
   - `データ源ごとに観測範囲が異なるため、画面時間とAIテレメトリ値を直接比較しません。`
5. `build_advice_evidence`にも観測窓差を測定限界として渡し、LLMへ直接比較を禁止する。
6. 旧statsに `source_windows` が無い場合は `観測範囲: 不明` とし、生成・表示を失敗させない。

### 非目標

- 異なるデータ源の値を比率換算して補正しない。
- 観測されていない時間を推計しない。
- ActivityWatchとAIテレメトリの時計を強制的に揃えない。

### テスト

- 最小・最大イベントから観測窓が正しく保存される。
- 日跨ぎイベントが対象日境界へクリップされる。
- 60分未満の差では警告なし、60分以上で警告あり。
- 片方が欠測でも例外にならない。
- 旧statsの読み込み互換。
- LLM向けevidenceに「直接比較しない」が含まれる。

## §Q3 [High] 「ツールエラー」を行動可能な失敗分類へ分解する

対象:

- `src/kaizenlog/aiwork.py`
- `src/kaizenlog/aiwork_codex.py`
- `src/kaizenlog/stats.py`
- `src/kaizenlog/advice_evidence.py`
- Activity LogのAI作業表示
- `tests/test_aiwork.py`
- `tests/test_aiwork_adapters.py`
- `tests/test_retry_chains.py`
- 新規 `tests/test_round12.py`

### 問題

現在の `tool_errors` は、終了コード非0、タイムアウト、拒否、接続不能、回復済みリトライ、監視用waitのyield等を同じ1件として数え得る。合計だけを `ツールエラー: 101回` と表示すると、作業が101回失敗したように見える。

### 必須修正

1. アダプタ共通のエラー分類を定義する。

```text
command_failed   終了コード非0、実コマンド失敗
timeout          明示タイムアウト
rejected         ポリシー・権限・ユーザー拒否
unavailable      実行ファイル・サービス・接続先なし
recovered        同一操作の後続試行で成功した失敗
unknown          上記に分類できない失敗
```

2. `wait` が「まだ実行中」「yield」「新しい出力なし」を返しただけの状態はエラーに数えない。
3. statsへ分類別件数を保存し、従来の `tool_errors` は後方互換用の合計として維持する。
4. 同一操作が後続試行で成功したことをログから確認できる場合、最初の失敗を `recovered` に振り替える。
   - 根拠なく推測しない。
   - 操作ID等で関連付けできない場合は元分類のまま。
5. Activity Logの主表示を次のように変える。

```text
ツール失敗: 101件（回復済み 82 / コマンド失敗 8 / タイムアウト 6 / 拒否 3 / その他 2）
未回復の可能性がある失敗: 19件
```

6. LLM evidenceには合計より先に「未回復の可能性がある失敗」を渡す。
7. `回復済み` が大半の場合、LLMが「作業が失敗続き」と断定しない測定限界を追加する。

### 非目標

- エラー内容から人間の能力や生産性を評価しない。
- 例外メッセージ全文や機密情報を日誌へ保存しない。
- 既存JSONLを書き換えない。

### テスト

- waitのrunning/yieldがエラー0件。
- 終了コード非0、タイムアウト、拒否、接続不能が各分類へ入る。
- 関連付け可能な失敗→成功が `recovered` になる。
- 関連付け不能な失敗は勝手にrecoveredへ移さない。
- 分類合計と後方互換 `tool_errors` が一致する。
- ログ本文・個人情報をstatsへ保存しない。

## §Q4 [High] データ不足時に「提案ゼロ」を許容し、根拠の弱いアクションを作らない

対象:

- `src/kaizenlog/advice_evidence.py`
- `src/kaizenlog/advice_format.py`
- `src/kaizenlog/advisor.py`
- `src/kaizenlog/memory.py`
- `src/kaizenlog/cli.py`
- `src/kaizenlog/prompts/daily_advisor.md`
- `src/kaizenlog/prompts/privacy_safe.md`
- `tests/test_advice_format.py`
- `tests/test_advice_evidence.py`
- `tests/test_advise_integration.py`
- 新規 `tests/test_round12.py`

### 問題

短時間データで「最大1件」としていても、スキーマが1件以上を要求すると、LLMは件数を満たすために根拠の弱いアクションを作る。

2026-07-26では、入力watcherが無いのに集中ブロックをPASS条件へ使い、記録にない「エンタメ検索ワードを含むタブ」を閉じる提案が生成された。第10弾は計測不能指標を拒否するが、それでも「何か1件出す」圧力が残る。

### 必須修正

1. `AdviceEvidence`に次を明示する。

```text
max_actions: 0..3
actionable_fact_ids: 計測可能で、提案に使ってよい事実ID集合
no_action_reason: string|null
```

2. 次の条件では `max_actions = 0` を許容する。
   - 合計観測時間120分未満。
   - かつ、計測可能な維持行動・明確な未回復失敗・実験中アクションのいずれもない。
3. `max_actions = 0` のとき、JSON契約は空の `proposals: []` / `actions: []` を正常値として受け入れる。
4. 表示は次の形にする。

```markdown
### 今日の結論
本日は観測時間が短く、追加の改善アクションを作る根拠がありません。

### 明日試すこと
今日は新しいアクションを追加しません。まず通常どおり記録を続けます。
```

5. 提案ゼロの場合:
   - KZN IDを発行しない。
   - Memoryへ追記しない。
   - 翌日ノートへ転記しない。
   - `advise` は終了コード0。
   - runlogへ `advice_action_count: 0` と理由を記録する。
6. `max_actions > 0` の場合、全proposal/actionの `fact_ids` は `actionable_fact_ids` と最低1件共有する。
7. daily_advisor / privacy_safeプロンプトに次を明記する。
   - 配列0件は失敗ではない。
   - evidenceに無いアプリ、タブ、検索語、通知、作業手順を創作しない。
   - 主要シグナルより優先度の低い事実を選ぶ場合は、機械可読な理由を要求しない。単純に選択対象から外す。
8. 「主要シグナル」はコード側で決める。
   - LLMに優先順位を自由判断させない。
   - 計測可能性、第10弾の既知指標、未回復失敗、現在実験、観測量を使った決定論的な候補集合に限定する。

### 非目標

- 毎日必ず改善点を作らない。
- エンタメ時間を一律に悪いと判定しない。
- 低データの日に大きな行動変容を提案しない。
- LLMにユーザーの意図・私生活を推測させない。

### テスト

- 120分未満＋actionable factなし → 提案0件、終了コード0。
- 提案0件 → KZN/Memory/翌日転記が増えない。
- 120分未満でも計測可能な実験中アクションがある → 最大1件を許容。
- `actionable_fact_ids` と交差しないproposal/actionは契約違反。
- evidenceにない「検索ワード」「タブ」等を含む実例相当回答が拒否される。
- 第10弾のfocus/site/ai指標可否ガードと重複せず、その結果を利用する。
