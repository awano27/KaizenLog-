## 背景

promptmine(繰り返し依頼のクラスタリング)は毎回ゼロから再計算する使い捨てで、記憶層がない。このため (1) kaizen-autopilot が**スキル化済み・却下済みのクラスタを翌週また提案**する、(2) 実験追跡は frontmatter への代表文の**手書きコピペ**(cluster_rep)頼み、(3) クラスタの初出・継続期間が追えない。KZN(提案)には Kaizen Memory があるのにプロンプト資産だけ記憶が無い非対称を解消する。

設計原則: Kaizen Memory と同じ**追記型後勝ち JSONL** / 安定ID / redact してから永続化(第18弾 §Q1 の title と同じ意図的例外)。

## §PR1 台帳モジュール(prompt ledger)

新規 `src/kaizenlog/promptledger.py`、`src/kaizenlog/memory.py`(採番・後勝ちパターンの流用元)

1. 保存先: `<vault>/Kaizen/Memory/prompt_clusters.jsonl`(追記専用・同一IDは後勝ち)。レコード: `{id, representative, count_total, days_seen, first_seen, last_seen, status, skill_name}`。`status` は `new | skilled | dismissed` の3値、`skill_name` は skilled 時のみ
2. ID: `PRM-YYYYMMDD-NNN`(初出日で採番、KZN と同じ形式)
3. **IDの安定性(最重要)**: クラスタ代表文は日によって揺れるため、単純な文字列一致では毎日別IDになる。upsert 時に既存台帳エントリと**promptmine が使うのと同じ正規化+類似度判定**(SequenceMatcher、クラスタリングと同じ閾値)で照合し、一致すれば既存IDを更新(count_total 加算・last_seen 更新・representative はより出現数の多い方に更新)、一致しなければ新規採番。この照合ロジックには専用テストを書く(「翌日わずかに違う代表文でも同一IDに合流する」ケースと「別の依頼は別IDになる」ケース)
4. **redact**: representative は `[privacy] redact_patterns` 適用後に保存する(依頼文の逐語はボールト同期で漏れ得るため。日誌原文主義の意図的例外である理由をコメントに明記)

## §PR2 cmd_prompts への統合

`src/kaizenlog/cli.py`(cmd_prompts)、`src/kaizenlog/promptmine.py`(render)

1. `kaizenlog prompts` 実行時にクラスタ結果を台帳へ upsert し、表示に PRM-ID と status を付ける(例: `PRM-20260729-001 [new] 5回/5日: ai-news: ニュースを要約して…`)
2. `--unhandled` オプション: status=new のみ表示(autopilot 向けの既定入力)
3. `kaizenlog prompts mark <id> skilled|dismissed [--skill NAME]`: 部分一致解決は `kaizenlog done` の規則(完全一致優先→サフィックス一致→曖昧なら候補表示+exit 1)を流用。skilled は `--skill` でスキル名を記録
4. 表示・保存とも cp932 で壊れない文字のみ

`src/kaizenlog/skills/kaizen-autopilot/SKILL.md`、`src/kaizenlog/weekly_context.py`、`src/kaizenlog/experiments.py`(参照のみ)
