# Codex 実装指示: アクション消化CLI(today/done)とヘルスレジャー — 第11弾

対象リポジトリ: `C:\develop\KaizenLog\KaizenLog-`(Python / pytest)

**前提: 第1〜10弾適用済みのワーキングツリー(特に第10弾 §M5 の notify 戻り値と runlog 記録を利用する)。** 実装順は §T3 → §T4 → §T1 → §T2 を推奨(T1 の先頭行が T3 の集計を使い、T2 が T1 の表示部品を再利用するため)。

## 背景

北極星指標(消化率)の最大の摩擦は「提案のチェックが Obsidian のノート内にしかない」こと。エンジニアは一日の大半をターミナルで過ごすため、`kaizenlog today` / `kaizenlog done` でターミナルから確認・消化できるようにする。あわせて、L2縮退(LLM契約違反時に提案を諦め事実サマリーのみ保存する非常灯)が**連続で点いていても誰も気づけない**問題に対し、advise 実行ごとの品質記録(ヘルスレジャー)を取り、ユーザーが毎日必ず通る場所(status / doctor / 朝通知 / today 先頭行)に配線する。**記録があるだけでは安全装置にならない。読まれる場所に出して初めて安全装置になる。**

設計原則(従来どおり厳守): 数字と判定はコードが決定論的に行う / マーカー区間の外は変更しない / 夜間・朝の無人実行を止めない / 追記型後勝ち JSONL と冪等性の既存パターンに乗せる / cp932 コンソールでも壊れない出力。

## §T3 ヘルスレジャー(advise 品質と実行時間の記録)

`src/kaizenlog/runlog.py`、`src/kaizenlog/advisor.py`、`src/kaizenlog/cli.py`

1. advise 実行ごとに品質記録を残す: `{date, backend, outcome, violations, duration_seconds}` を runlog の既存 JSONL 様式(追記・retention)に乗せる。`outcome` は `ok`(一発成功)/ `repaired`(修復1回で成功)/ `degraded`(L2縮退保存)/ `failed`(例外終了)の4値。`violations` は契約違反の種別リスト(修復・縮退時のみ、本文は含めない — プロンプト・提案本文を記録に残さない。この理由をコメントに明記)
2. 記録点は advisor の修復・縮退の分岐(契約違反 → 修復 → 縮退の既存経路)と cli の advise 完了/例外ハンドラ。**記録失敗は握り潰して本処理を続行**(既存の静かな故障対策と同じ原則)
3. 集計ヘルパーを追加: (a) 直近 N 日の `degraded/failed` の**連続回数**(最新日から遡って数える)、(b) コマンド別 `duration_seconds` の中央値と最大(既存 runlog 履歴を利用)。いずれも純粋関数としてテスト可能にする

テスト: 4値それぞれの記録が正しい outcome で残る / violations に本文が含まれない / 連続回数の計算(途中に ok が挟まると リセット)/ duration 集計。

## §T4 ヘルスの配線(status / doctor / 朝通知)

`src/kaizenlog/cli.py`(status)、`src/kaizenlog/doctor.py`、morning の通知組み立て

1. `kaizenlog status` に �ルス行を追加: 直近 advise の outcome、縮退/失敗の連続回数、直近 duration が中央値の2倍を超えていれば「実行時間が悪化(LLMタイムアウト接近の可能性)」警告
2. `kaizenlog doctor` にチェックを追加: 縮退または失敗が**2回以上連続**なら error(「提案が連続して縮退しています。LLM出力が契約に合っていません」)、1回なら warn。既存チェック一覧の様式に合わせる
3. 朝の通知(morning の `build_morning_notification`)と §T1 の today 先頭行に、昨夜が `degraded/failed` だった場合のみ1行追加: `⚠ 昨夜の提案は縮退しました(N日連続)`。**提案本文・違反内容は通知に載せない**(ロック画面対策の既存原則)

テスト: 連続縮退2回で doctor が error / 1回で warn / 正常時は表示なし / 通知文言の組み立て(N日連続の数字)。

## §T1 `kaizenlog today` — ターミナルから今日のアクションを見る

`src/kaizenlog/cli.py`、`src/kaizenlog/memory.py`

1. 新サブコマンド `kaizenlog today [--date YYYY-MM-DD]`(省略時は今日)。処理順:
   1. **ノートのチェック同期**: 既存の「未完了エントリの提案日ノート走査」(cmd_advise が行っているのと同じ update_statuses_from_note の経路)を実行し、Obsidian 側で付けたチェックを Memory に反映してから表示する(表示が古いと信頼を失うため。この理由をコメントに明記)
   2. **ヘルス警告行**(§T4 の条件に該当する場合のみ先頭に1行)
   3. **北極星行**: 既存 `compute_action_stats` を再利用(`直近14日: 消化率 42%(12件中5件)/ PASS率 75%` 様式は既存表示に合わせる)
   4. **未完了アクション一覧**: 提案日が過去7日以内の `proposed` エントリを新しい順に表示。書式: `KZN-20260726-001  [7/26]  ✅PASS  <アクション本文1行>`(verdict があれば絵文字、なければ空欄)。ID は後続の `done` でそのままコピペできる形で出す
2. 0件のときは「未完了のアクションはありません」+ 北極星行のみ。exit 0
3. 出力は既存の cp932 対策(reconfigure)の範囲で壊れない文字のみ(絵文字は既存ノート出力で使用実績のあるものに限る)

テスト: チェック同期後に表示が変わる / 7日窓の境界 / verdict 絵文字の有無 / 0件時の出力と exit code。

## §T2 `kaizenlog done <id>` — ターミナルからアクションを消化する

`src/kaizenlog/cli.py`、`src/kaizenlog/memory.py`、`src/kaizenlog/vault.py`

1. 新サブコマンド `kaizenlog done <id>`。`<id>` の解決規則:
   - 完全一致(`KZN-20260726-001`)を最優先
   - 部分一致は「未完了(proposed)エントリの ID 末尾」に対するサフィックス一致(例: `001`、`26-001`)。**一意に定まらなければ候補一覧を表示して exit 1**(誤爆消化を防ぐ。この理由をコメントに明記)。該当なしも exit 1
2. 消化の記録: 追記型後勝ち JSONL に `status=done` と **`done_date=今日`** を追記する(`done_date` フィールドが未定義なら後方互換で追加 — 既存行は欠損許容。第10弾 §M2 の判定基準日がこのフィールドを使う)
3. **ノートへの同期**: 当日ノートの ACTIONS 区間を最新の Memory 状態で再描画する(既存の `render_actions_section` → `write_section(position=設定値)` の経路を再利用。該当エントリのチェックボックスが `- [x]` で描画されること、他エントリのチェック状態が保持されることは既存実装が担保)。当日ノートが無ければノート同期はスキップして Memory 記録のみ(警告表示)
4. 成功時の出力: 消化したエントリの ID と本文、更新後の消化率を1行(「消化率 45% に上がりました」的な即時フィードバック。北極星への寄与を見せる)

テスト: 完全一致/サフィックス一致/曖昧(複数候補で exit 1)/該当なし(exit 1)/ done_date が今日で記録される / ノート再描画でチェック保持 / ノート不在時のスキップ / 冪等(同一 ID を2回 done しても JSONL 後勝ちで壊れない)。
