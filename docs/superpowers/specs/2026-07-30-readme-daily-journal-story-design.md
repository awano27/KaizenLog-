# KaizenLog README — 日誌・振り返り訴求の改善設計

**日付:** 2026-07-30

**状態:** ユーザー承認済み（3職種の縦並びミニ日誌へ改訂）

**対象:** `README.md` の「毎日の記録として使う」周辺

## 目的

KaizenLogをAI作業専用の分析ツールに見せず、次の2つを同時に伝える。

1. PC作業から、AIを使わない日でも役立つ業務日誌を作れる。
2. 自動記録と本人の振り返りを組み合わせ、翌日の行動改善につなげられる。

READMEを読む人が、導入後にどのような日誌が残り、何を振り返れるのかを具体的に想像できる状態を成功とする。

## 読者と伝える価値

**主な読者:** Windowsで日々のPC作業を行い、Obsidianへ記録を残したい個人開発者、知識労働者、業務改善担当者。

**一文の価値:** KaizenLogは、一日のPC作業を自動で業務日誌にし、自分の言葉による振り返りと翌日の小さな改善へつなげる。

**最初に示す証拠:** 開発者、企画・営業、ライター・研究者の3職種で、一日の記録と振り返りがどう見えるかを示す短い架空例。

## 採用する構成

現行のREADME全体やSVGは作り直さず、「毎日の記録として使う」節を文章中心に拡張する。見出しは次へ変更する。

> `## 毎日の記録と振り返りに使う`

節内の読み順は次のとおりとする。

1. `朝に目標を書く → 日中は自動記録 → 夜に振り返る → 必要な場合だけAI提案`という一日の流れ
2. 3職種の架空のミニ日誌
3. 自動記録、本人の振り返り、本人が決める翌日の目標の違い
4. Activity LogとLLMの正確な境界
5. 既存の`run`、`morning`、`today`運用説明

## 3職種のミニ日誌

横幅の広い比較表や、完全なActivity Logの技術的な転載は使わない。スマートフォンでも読みやすいように、3職種を縦に並べる。各例は必ず次の3行で構成する。

- **自動記録:** Activity Logから分かる合計アクティブ時間と主なカテゴリ別時間
- **自分の振り返り:** 本人がObsidianへ書く感想や違和感
- **明日の目標:** 本人が`kaizenlog goal`で設定する次の一歩

サンプル全体の前に、数値・文章ともに架空であり、利用者データ、導入実績、改善効果ではないと明記する。カテゴリ名は導入先の設定で変えられるため、以下は用途を伝える例として扱う。

### ソフトウェア開発者

- **自動記録:** `6時間12分｜実装 3時間05分｜レビュー 1時間20分｜会議 50分`
- **自分の振り返り:** `会議後に開発へ戻るまで時間がかかった`
- **明日の目標:** `午前中にレビュー対応を終える`

### 企画・営業

- **自動記録:** `5時間48分｜顧客会議 2時間10分｜提案書 1時間45分｜調査 1時間05分`
- **自分の振り返り:** `会議が続き、提案書の作成が夕方に偏った`
- **明日の目標:** `最初の会議までに提案書の骨子を作る`

### ライター・研究者

- **自動記録:** `5時間30分｜執筆 2時間35分｜調査 1時間50分｜推敲 45分`
- **自分の振り返り:** `午前の調査が長引いたが、午後は執筆に集中できた`
- **明日の目標:** `調査を90分で区切り、初稿へ進む`

各例のカテゴリ時間は主な内訳であり、合計時間の完全な内訳とは表現しない。本人の振り返りと明日の目標は自動生成された文章ではない。

## 例の後に置く正確性の境界

3例の直後に、次を短く明記する。

- Activity LogはActivityWatchが観測したPC前景活動であり、勤務時間、目標達成、集中力、生産性の判定ではない。
- スマートフォン、他デバイス、離席中の行動は既定では測定できない。
- 入力watcherから統計を取得できる場合は、現行実装の`25分以上`を基準とする集中ブロックも表示できる。
- 日誌生成と本人の振り返りにはLLMが不要である。
- 本人の振り返りを改善提案へ反映するときだけ、設定済みLLMバックエンドを使う。

## 目標・手書き振り返り・LLMの関係

3例の後に、操作を一つずつ説明する。朝は次のコマンドで当日の目標を記録できる。

```powershell
kaizenlog goal "提案書の初稿を完成させる @執筆・ノート"
```

夜は同じObsidianの日誌へ本人が自由に記入できる例を示す。

```markdown
## 振り返り

午前は執筆に集中できた。午後は会議後の再開に時間がかかった。
```

KaizenLogは管理マーカー区間だけを更新し、その外側にある手書き本文を置換しない。`## Reflections`または`## 振り返り`の本文があり、LLMによる`advise`を実行する場合は、本人の言葉を優先文脈として提案へ渡す。

ここでは次の境界を明記する。

- `generate --date YYYY-MM-DD`によるActivity Log生成はLLMなしで使える。
- 手書きの振り返り自体にもLLMは不要である。
- 振り返りを改善提案へ反映する処理だけが、設定済みLLMバックエンドを使う。
- `backend = "none"`で`advise`を実行すると、提案をスキップして成功扱いにせず、エラーで終了する。

## 既存運用説明の扱い

現行の次のコマンドは削除しない。

```powershell
kaizenlog run
kaizenlog morning
kaizenlog today
```

日誌の価値と例を先に示した後で、現在の正確な説明を残す。

- `run`は`generate`と`advise`を順に実行する。
- `morning`は未完了アクションの再表示と、必要に応じた追いつき処理を行う。
- `today`は候補を確認し、`done`で完了にできる。
- 日々のLLM提案は現在の契約どおり1〜3件である。

## 正確性と非目標

### 必ず守ること

- ActivityWatchが観測するPC前景アプリを中心とした記録であると分かるようにする。
- スマートフォン、他デバイス、離席中の行動を含む完全な生活記録とは主張しない。
- アクティブ時間を勤務時間と呼ばない。
- カテゴリ時間の変化だけで改善や達成を断定しない。
- 手書き本文をKaizenLogが自動生成したように見せない。
- 架空サンプルを実利用データ、導入実績、効果測定結果として見せない。
- 3職種のカテゴリ別時間を合計時間の完全な内訳とは説明しない。
- 集中ブロックの閾値は現行コードの`25分以上`と一致させる。

### 今回行わないこと

- Python実装、CLI、設定、日誌フォーマットの変更
- README用SVGの追加・変更
- M365 CopilotやChrome拡張の説明変更
- 実データ、ActivityWatch、Obsidian、LLMへの接続
- `docs/USAGE.md`の書き換え

## 受け入れ条件

- 「どのような日誌ができるか」を3職種の例から数秒で理解できる。
- 3職種が縦並びで、各例の`自動記録`、`自分の振り返り`、`明日の目標`をスマートフォンでも追いやすい。
- 大きな技術的Activity Log表を使わず、AIを使わない業務改善用途が平易な日本語で示されている。
- 朝の目標、夜の振り返り、任意のLLM提案という一日の流れが理解できる。
- サンプルと説明が現在のコード上の出力・境界と一致している。
- 既存の改善ループ、M365の未実装表示、プライバシー境界を壊さない。
- 永続的な変更は`README.md`、`tests/test_readme_contract.py`、本仕様・実装計画に限定される。
