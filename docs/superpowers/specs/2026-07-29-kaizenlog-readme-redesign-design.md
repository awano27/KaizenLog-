# KaizenLog README 再設計

日付: 2026-07-29

状態: ユーザー承認待ち

対象: `README.md`、`assets/readme/*.svg`

## 1. 目的

GitHubを初めて訪れた日本語話者のWindows／Obsidianユーザーに、KaizenLogの価値を最初の5秒で伝える。

中心メッセージは次の1文とする。

> 一日のPC作業を、明日の改善1つに変える。

機能一覧から始めず、「散らばった作業ログが、Obsidianの日誌と具体的な次の行動に変わる」という利用者の変化から見せる。

## 2. 対象読者

主対象:

- Windowsで日々PC作業をする人
- ActivityWatchで活動を記録している、または記録したい人
- Obsidianのデイリーノートに振り返りを残したい人
- AIの提案を無条件に採用するのではなく、記録を根拠に小さく改善したい人

副対象:

- インストール前にデータの送信範囲や制限を確認したい人
- 開発、拡張、コントリビュートを検討する人

## 3. 採用する方向

採用案は「A: 変化を一撃で見せる」。

ヒーローでは、表示例として次の変化を大きく見せる。

```text
今日のPC作業 6h42m
        ↓
明日の一手 1件
□ 9:00に25分の集中枠を入れる
```

`6h42m`は製品の実績値やベンチマークではないため、必ず「表示例」と明記する。数値そのものではなく、「大量のログが1つの具体的な行動に絞られる」対比を視覚的な主役にする。

## 4. 情報設計

READMEは次の順番で構成する。

1. ヒーロー
   - 製品名
   - 中心メッセージ
   - `6h42m → 1 ACTION`の表示例
   - Windows／ActivityWatch／Obsidian向けであること
2. 実際に残るMarkdown
   - Activity Log
   - 今日の結論
   - 明日試すこと
   - 計測上の注意
3. 最短の初回体験
   - `kaizenlog setup`
   - `kaizenlog doctor`
   - `kaizenlog generate`
   - まず手動実行で成功を確認する
4. 毎日の改善ループ
   - 夜: 計測結果を日誌化
   - 朝: 前日の記録を確認
   - 日中: 改善を1つ試す
5. 安心して使うための説明
   - LLMバックエンド
   - LLMに渡す情報のマスキング
   - Obsidianへの書き込み範囲
   - 自動実行が有効になる条件
6. 任意機能
   - Claude Codeスキル
   - watcher
   - ブラウザAIテレメトリ
7. 制限・開発・ライセンス
   - 計測上の限界
   - 分類カスタム
   - 開発手順
   - ロードマップ
   - ライセンス

長い説明は折りたたみに逃がさず、最初に必要な判断材料は本文内で短く提示する。詳細ドキュメントへのリンクは、その後に置く。

## 5. 初回体験の設計

最短導線は `setup → doctor → generate` とする。

`run`はLLMや外部サービスの設定による失敗要因が増えるため、最初の成功条件には含めない。まず環境診断と日誌生成を成功させ、その後でLLMを使った提案や日次運用を案内する。

インストールは現在の配布状態に合わせ、未公開のPyPI安定版が存在するような表現をしない。ソースからの`pipx`インストールを主導線とする。

## 6. ビジュアルシステム

方向名: Daily Ledger

配色:

- 背景: `#0B1211`
- 主文字: `#F4F0E8`
- 計測・進行: `#75CFA3`
- 次の行動: `#F0B667`
- 補足: `#81958C`

タイポグラフィ:

- 見出し: GitHub上で読みやすいシステムサンセリフ
- 時刻、コマンド、ID: 等幅フォント

モチーフ:

- 時刻付きの活動ログ
- Markdown記号
- チェックボックス
- `KZN-001`などの改善ID
- 薄い台帳グリッド

派手なグラデーション、装飾目的の大量バッジ、外部フォント、外部画像サービス、GIFは使わない。インパクトは色数や動きではなく、「ログ量と改善1件の落差」「実際の出力」「明確な導線」で作る。

既存の次の4ファイルを同じビジュアルシステムで再制作する。

- `assets/readme/hero.svg`
  - `6h42m → 1 ACTION`の変化
  - 中心メッセージ

  - `NIGHT → MORNING → TODAY`

  - ActivityWatch → KaizenLog → Obsidian

要件:

- 外部画像、外部フォント、JavaScriptに依存しない純SVG
- GitHubのライト／ダーク背景の両方で境界と文字が読める
- SVG単体でも内容が伝わる`title`と`desc`を含める
- モバイル幅で縮小されても主要メッセージが判読できる

## 8. 文章のルール

- 日本語を主言語とし、英語は製品名、コマンド、短いラベルに限定する
- 「完全オフライン」「自動で必ず登録される」など、設定条件を省略した断定をしない
- LLM利用は任意であることを明示する
- マスキング対象はLLMへ送るプロンプトであり、ローカルの元日誌そのものではないと区別する
- タスク登録は対話中の承認または`--register-task`を選んだ場合に行われると説明する
- ActivityWatch、Obsidian、LLM、KaizenLogの責任範囲を混同しない
- 未確認の性能値、利用者数、成功率は載せない

## 9. レスポンシブ・アクセシビリティ

- 画像に頼らず、直後の本文でも同じ意味を説明する
- 色だけで状態を区別しない
- 見出し階層を連続させる
- 画像の代替テキストは内容を説明する
- 長い表は避け、モバイルでは縦に読める構成にする
- 横スクロールを発生させない

## 10. 変更対象と非対象

変更対象:

- `README.md`
- `assets/readme/hero.svg`
- `assets/readme/section-start.svg`
- `assets/readme/section-loop.svg`
- `assets/readme/workflow.svg`

非対象:

- CLIやアプリ本体の機能変更
- パッケージ公開
- GitHub Releasesの作成
- データベース変更
- `docs/HANDOFF.md`を含む既存の未追跡ユーザーファイル

## 11. 受け入れ条件

- README冒頭だけで「誰向けか」「何がどう変わるか」が理解できる
- `6h42m`が表示例であることを誤認しない
- 実際のMarkdown出力例がヒーロー直後にある
- 初回導線が`setup → doctor → generate`で統一される
- LLM、自動タスク、マスキングの条件が正確
- 4つのSVGが同じDaily Ledgerスタイルで統一される
- GitHub Markdownとしてリンク、画像、見出し、コードブロックが成立する
- デスクトップ幅とモバイル幅で主要情報が読め、横スクロールしない
- README監査スクリプトとリンク／SVG検証が成功する
- `docs/HANDOFF.md`など対象外ファイルを変更・ステージしない

## 12. 検証方法

1. `beautify-github-readme`の監査スクリプトをREADMEへ実行する
2. README内のローカル画像・リンク先が存在することを確認する
3. 4つのSVGをXMLとして解析できることを確認する
4. READMEプレビューをデスクトップ幅とモバイル幅で表示確認する
5. README内のコマンドを現行CLIヘルプと照合する
6. `git diff --check`で空白エラーを確認する
7. `git status --short`で対象外ファイルが変更されていないことを確認する
