## 診断: 価値が頭打ちになっている3つの原因

### 1. 出力帯域が構造的に細い — LLM出力の大半を捨てている

`render_reader_advice`（[advisor.py:570-589](../src/kaizenlog/advisor.py:570)）は、契約検証を通した LLM 回答から **チェックボックス行だけ** を正規表現で抜き出し、`interpretation` / `next_metric` / `ai_review` / `plan_review` を丸ごと破棄している。

```python
def render_reader_advice(advice_md: str, evidence: AdviceEvidence) -> str:
    sections = _level3_sections(advice_md)
    actions = _ACTION_RE.findall(sections.get("明日の最小アクション", ""))
    ...
    return ("## 🚀 Kaizen（AIからの改善提案）\n\n"
            "### 今日の結論\n\n" f"{evidence.reader_summary}\n\n"   # ← 決定論3文
            "### 明日試すこと\n\n" + "\n".join(rendered_actions)     # ← LLMはここ1行のみ
            + "\n\n### 計測上の注意\n\n" + notes)                    # ← 決定論
```

結果、`advise` 所要 ~260秒 / 出力の大半を検証してから捨てており、**LLM 呼び出しに対する情報還元が最も低い**。読者面に届くのは「決定論3文 + チェックボックス1行 + 定型注記」だけになっている。

### 2. 単日スナップショットに固定されている

stats は6日分が揃い、AI作業が **44.3 → 49.0 → 59.1 → 77.8 → 114.4分（5日連続増・約2.6倍）** という最大の変化を決定論で算出できる。しかし日誌に比較軸が1本もなく、結論3文のうち2文は直上 Activity Log の逐語再掲：

| 日 | 合計 | cs | AI作業 | tool_errors | retry |
|---|---:|---:|---:|---:|---:|
| 7/26 | — | 106 | 44.3 | 101 | 0 |
| 7/27 | — | 160 | 49.0 | 770 | 0 |
| 7/28 | — | 261 | 59.1 | 121 | 0 |
| 7/29 | — | 236 | 77.8 | 178 | 0 |
| 7/30 | 219.5 | 210 | 114.4 | 639 | 3 |
| 7/31 | 44.9 | 77 | 14.1 | 4 | 0 |

7/31 は全指標が改善方向（エラー 639→4、リトライ 3→0）なのに、**日誌のどこにも正の情報が出ない**。摩擦とエラーだけが並び、続ける動機が生まれない構造。

### 3. 判定機構の信頼が壊れている

**(a) 同一日の判定が3本積まれ、ノートが自己矛盾している。**

`suggestions.jsonl` の KZN-20260729-002（実データ）:

```
verdict=None
verdict=pass  value=79.0   verdict_date=2026-07-30
verdict=pass  value=181.0  verdict_date=2026-07-30
verdict=fail  value=210.0  verdict_date=2026-07-30
```

`judge_entries` を当日 summary で呼んでおり（[cli.py:443](../src/kaizenlog/cli.py:443)）、[verdict.py:155-200](../src/kaizenlog/verdict.py:155) に測定日完了検査が無い。転記行を書く経路は `day+1` のノートしか更新しないため、最初の ✅79 が凍結する。実際に `2026-07-30.md:11` が「判定 ✅ 実測79」、同ファイル `:21` が「コンテキストスイッチ: 210回」で**同一ノート内で矛盾**している。

**(b) 学習ループが一度も起動していない。**

`suggestions.jsonl` 全26行の status は `proposed` 25 / `superseded` 1 で、**`done` が0件**。`done` はユーザーが Obsidian で `- [x]` を手で入れたときだけ付く（[memory.py:216-240](../src/kaizenlog/memory.py:216)）。そして較正・棄却・風化の3機構はすべて `status == "done"` を入口にしている：

- `metric_pass_rates` — [memory.py:498](../src/kaizenlog/memory.py:498) `if e.status != "done": continue`
- `consecutive_fail_actions` — [memory.py:583](../src/kaizenlog/memory.py:583) `if e.status == "done"`
- `detect_kzn_decay` — [decay.py:197](../src/kaizenlog/decay.py:197)

つまり **設計上は完成している学習ループが、本番で一度も発火していない**。第12〜15弾・第29弾で作った較正機構が全て空回りしている。

**(c) PASS指標が行動ではなく稼働時間を測っている。**

PASS指標の語彙（[advisor.py:83-100](../src/kaizenlog/advisor.py:83)）は全て生の日次カウントで、率・正規化指標が1つもない。実測で検算すると：

| 日 | cs（生） | 稼働 | cs/時 | `context_switches <= 185` |
|---|---:|---:|---:|---|
| 7/30 | 210 | 219.5分 | **57.4回/時** | ❌ |
| 7/31 | 77 | 44.9分 | **102.9回/時** | ✅ |

**生カウントと1時間あたりで順位が完全反転する。** KZN-20260729-002 の ✅→❌ の反転は行動の変化ではなく稼働量の変化。`advice_evidence.py:138` は回/時を計算済みだがLLMプロンプト行止まりで、`experiments.py` の指標定義にレート系が1つもない。
