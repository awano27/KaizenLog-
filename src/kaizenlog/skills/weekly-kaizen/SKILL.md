# Weekly Kaizen

決定論の集約結果を根拠に、日次では見えない傾向と次の実験を書く。

## 対象と一次データ

1. `--week YYYY-Www` の指定があればその週、なければ設定の `general.timezone` の
   今日を含む月曜始まりの週を使う。既存設定のVaultと対象週を確認し、以後固定する。
   設定を明示された場合は、すべてのコマンドに同じ `--config` を渡す。
2. 許可されたコマンド実行ツールで次を実行する。

   ```sh
   kaizenlog --config "<既存の設定TOML>" weekly-context --week YYYY-Www --write --strict-write
   ```

   確認済みの既定設定なら `--config` を省略できる。終了コード0と保存先を確認してから、
   対象ノートの `<!-- kaizenlog:weekly-context:start -->` ～ `end -->` 区間を読む。
   設定で指定されたdaily notesディレクトリの `Weekly Reviews/YYYY-Www.md` が保存先。
   CLIがない、実行できない、保存が失敗した場合は理由を報告して停止する。
   古いマーカー区間を今回の集約結果として使わない。手集計へ切り替えない。
3. 集約結果で疑問が残る場合だけ、該当日のノートや関係するプロジェクト・実験ノートを読む。
   対象週末より後の実測値を混ぜない。全実験ノートや生の会話ログを一括で読まない。

## 分析と記録

- カテゴリ時間、AIテレメトリ、目標と実働の差、提案の消化率・PASS率は
  集約済みの数値を引用する。再計算せず、記録なし日と測定限界を明記する。
- 実験の実測は対象週末まで。台帳の状態や採否は「現在の状態」を含むため、
  当時の状態と断定しない。採否推奨はコードの表示を使い、人間の最終判断がある場合だけ
  `status` を `adopted` / `rejected` に更新する。
- 摩擦セッションを考察する場合だけ、[AI作業レビューの観点](references/ai_work_deep_review.md)
  を読む。エラー・中断・リトライは観測事実として扱い、原因は仮説と区別する。
  依頼文・応答・検証結果が揃わなければ品質は `Unknown`。1～5の採点や拒否理由を作らない。
- 繰り返し依頼は集約の「プロンプト資産」を参照する。これは現在の台帳の補助情報であり、
  対象週だけの発生件数とは限らない。実行日基準の `prompts --days 7` で補完しない。
- 数値低下だけで改善、未チェックだけで無視、中断だけで出力拒否と断定しない。
  カテゴリ変更は通知数ではなく、短いAIセッションは中立、PC外の行動は未測定。

考察は同じレビューノートの**weekly-contextマーカー区間の外**へ書く。
既存の手書き考察を保持し、同じ内容を重複追記しない。必要な節だけ使う:

- 週間サマリーと計画との差
- AI作業の観測事実・仮説・Unknown
- 日次提案の現在の追跡結果と、実験の実測・採否推奨
- 来週の実験（最大3件、合図・行動・測定指標・期限）
- 対象日のノートと根拠へのリンク

## 次の実験と完了

レビューで起票する実験は、既存の `kaizenlog experiment new` を使う。
`--metric`・`--target`・`--days` は計測できる内容にする。過去週のレビューから
今起票する場合は、実際の開始日を明記し、過去に実験したように書かない。
起票できなければ候補として残し、作成済みと報告しない。

対象週のデイリーノートには週次レビューへのリンクがなければ1つ追加する。
手書き部分と他のkaizenlogマーカー区間は変更しない。
完了報告には対象週、保存先、作成した実験、記録不足・失敗・未実施を含める。
