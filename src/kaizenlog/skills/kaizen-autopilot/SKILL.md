# Kaizen Autopilot — 自己実装するカイゼン

あなたの仕事は、繰り返しパターンを**提案で終わらせず、動く自動化として提出する**こと。
有効化が未承認なら、**人間がレビューできるPR / 提案ノートまで完成させて提示する。**
同じ対象・内容について既に得た承認は引き継ぎ、その範囲の作業と検証を完了する。

## 手順

1. **パターン検出**: 次の2つを実行し、レポートを読む。
   - `kaizenlog patterns --days 14`（行動の繰り返しパターン）
   - `kaizenlog prompts --unhandled --days 14`（プロンプト資産化の**未処理**候補のみ。
     status が skilled / dismissed のクラスタは台帳で除外済みなので**提案しない**）
   コマンドが使えない場合はボールトの `.kaizenlog/stats/*.json`（日次統計）を直接読んで
   同等の分析をする。データが3日分未満なら「データ不足」と報告して終了する。

2. **候補の選定**: 検出されたパターンから、**最大2件**だけ選ぶ。選定基準:
   - 内容が定型で、自動化の成果を数値（時間・回数）で検証できる
   - 実装が1〜2ファイルに収まる小ささ
   - 判断に迷う場合は実装せず、ユーザーへの質問として提案ノートに書く

3. **実装方針の決定** — パターン種別ごとの定石:
   - **定時ルーチン**（毎朝のニュース巡回、定型レポート作成など）
     → スクリプトと登録手順、またはClaude Codeスキルと
       `claude -p` の定期実行手順を作る。有効化は承認された時点で行う
   - **AI作業の摩擦**（特定リポジトリで細切れ・エラーが慢性化）
     → 摩擦の原因をコードや既存手順で確認できた場合に、ビルド/テスト手順・前提・制約の
       追記案を作る。短セッションやエラー数だけで文書不足と断定しない。
       頻出依頼があればスキル案に切り出す
   - **時間泥棒**（エンタメ等）
     → コードでは解決しない。カイゼン実験の起票だけにとどめる
   - **繰り返しプロンプト**（`kaizenlog prompts --unhandled` で検出された頻出依頼）
     → レビュー用ブランチ、または自動読み込み対象外の下書きディレクトリに
       `<内容のslug>/SKILL.md` を作る。実運用の `.claude/skills/` への配置は有効化に含む。
       依頼の共通部分（前提・制約・出力形式）をスキル本文に固定し、変動部分を引数にする。
       あわせてボールトの `04 Resources/Prompt Library.md` に「発掘したプロンプト→
       スキル/テンプレの対応表」を追記する（無ければ作成）。ノートには生のプロンプト
       全文ではなく要約を書くこと（機密が含まれ得るため）。
       **承認され、実運用先への配置を確認できたら**
       `kaizenlog prompts mark <PRM-ID> skilled --skill <名前>` を実行する。
       下書き・未マージPRの段階では skilled にしない。再提案前に対応表の下書き/PRを確認する。
       明示的に却下された候補だけ `kaizenlog prompts mark <PRM-ID> dismissed` で記録する。

4. **実装と提出**:
   - 対象が**gitリポジトリ内**の場合:
     ブランチ `kaizen/auto-<内容のslug>` に実装し、必要な検証を行う。
     コミット・push・PR作成は、その対象と内容について承認された範囲で行う。
     外部公開の承認がなければローカル差分とPR文面を完成させて提示する。
     PR本文には「根拠となったパターン（検出レポートの該当部分）」「期待効果」
     「検証結果」「有効化の手順」を書く。
     **mainへの直接コミット・マージは絶対にしない。**
   - 対象がgit管理外（ボールトのスクリプト等）の場合:
     ファイルを作成した上で、`00 Inbox/` に提案ノート
     `🤖 自動化提案 YYYY-MM-DD <タイトル>.md` を作り、何を作ったか・どう有効化するか・
     どう元に戻すかを書く。**タスクスケジューラへの登録などの有効化は行わない。**

5. **効果測定の実験を準備**: 実装した自動化1件につき、効果を検証する実験案を1つ作る。
   有効化前は提案ノートに指標・目標・期間を残し、有効化の確認後にその日を開始日として起票する。
   下書きの期間を「改善後」の測定期間に含めない。
   例: ニュース巡回を自動化したら
   `kaizenlog experiment new --title "朝のニュース巡回を自動化で置換" --metric "category_minutes:ブラウジング" --target "<= 30" --days 14`
   コマンドが使えなければ `03 Areas/Kaizen Experiments/` に既存実験と同じ形式で直接書く。

   **繰り返しプロンプトをスキル化した場合**: 生依頼が減ったかを測るため、
   実験案（有効化後は実験ノート）に次を入れる:
   - `metric: prompt_cluster:<slug>`（slug はスキル名など）
   - `cluster_id: PRM-YYYYMMDD-NNN` — 台帳 ID を優先（手書き代表文のコピペミスを防ぐ）
   - （後方互換）`cluster_rep: <正規化代表文>` — ID が無い旧ノート用。
     **機密を含む生の依頼全文をそのまま書かない**
   - `target: "<= 0"`（スキル化後は同型の生依頼が0件/日を目標）
   - `deadline` は14日後
   毎晩の `generate` が `cluster_id`（なければ `cluster_rep`）類似の依頼件数を自動計測する。

6. **報告**: 最後に以下を簡潔にまとめる:
   - 実装した自動化（ブランチ/PR/提案ノートへのリンク）
   - 見送った候補とその理由
   - 実験案と、実際に起票した実験を区別して記載
   - 下書き・公開済み・有効化済みの状態と、残っている承認

## 安全規則（違反禁止）

- 1回の実行で実装するのは最大2件
- 同じ対象・内容について既に得た承認を引き継ぐ。スキル呼び出しだけで外部公開や有効化の承認を推測しない
- main/masterブランチへ直接コミットしない。マージしない
- 既存のタスクスケジューラ・cron・常駐プロセスを変更・削除しない
- 認証情報・APIキーをコードやノートに書かない
- 破壊的操作（ファイル削除、履歴書き換え）をする自動化は提案のみにとどめる
- 同じ内容の提案が過去のPR/提案ノートで却下されていたら再提出しない
